# ADR-0027: The edge set is published as one table per endpoint pair

Date: 2026-11-11
Status: RULED & LANDED 2026-11-11

## 1. Context

A reader wants to ask graph questions of the lake with SQL/PGQ: declare a property graph over the published tables and match paths in it. That declaration is the reader's DDL — a session or catalog object rebuilt from a script — so nothing about the graph itself is exported. What must be exported is a table shape the declaration can name.

The declaration needs two things our canonical edge table does not offer. An edge table's endpoint columns must EQUAL a vertex table's key columns (`SOURCE KEY (src_scope, src_node_id) REFERENCES entities (scope, node_id)`), and each `EDGE TABLES` entry references exactly ONE vertex table. Our edge batch carries `(src_table, src_pkey)` — a name and the endpoint's raw key bytes — and it spans vertex tables, because a fact may point at an entity or at a member.

## 2. Decision: one table per endpoint pair, typed endpoints, canonical columns kept

The edge set is published as `facts__<src>__<dst>` — `facts__entities__entities`, `facts__entities__members`, `facts__members__entities`, `facts__members__members`. Each carries the canonical columns unchanged (`src_table`, `src_pkey`, `dst_table`, `dst_pkey`, `predicate`, the edge key, the payload fields, `variant`) and, before the variant, the endpoint keys DECODED into the columns of the vertex table that pair names:

- `entities` — `src_scope u64`, `src_node_id u64` (and `dst_*`);
- `members` — `src_member_id` as hyphenated text, the same spelling the vertex table writes.

The pairs are enumerated, not discovered: a pair with no edge is published as an EMPTY table. That makes the published set a function of the declaration rather than of today's rows, so a reader's declaration never has to change when the first edge of a new kind appears.

The raw key columns stay. A restore needs the exact bytes, and keeping them means a reader joining an edge to a node never has to learn the key codec.

## 3. What this costs and what it buys

The lake's table count grows as the square of the vertex tables (two today: four edge tables). A new vertex table adds a row of pairs, each published empty until it holds an edge.

okm's edge import now finds its columns BY NAME and tolerates extras, so a pair table is still what a restore feeds the graph — the typed columns are simply not its business. That is the whole reason the pair split costs no restore code: the table a reader declares a graph over and the table a restore reads are the same table.

## 4. Rejected

- **One wide edge table with nullable typed columns** (`src_scope`, `src_node_id`, `src_member_id`, … with one family non-null per row). SQL/PGQ's endpoint columns must not be null: a NULL endpoint does not fail, it quietly matches nothing, and a graph query that silently sees no edges is worse than one that refuses to compile.
- **Keeping one canonical edge table and letting the reader build N views.** Views are local DDL, like the graph itself, so this costs no bytes — but it moves a shape decision onto every reader and makes "can I graph this lake" depend on someone writing the view. Explicitly traded away in favour of the lake being graphable as published.
- **Dropping the raw key columns.** Then a restore either decodes nothing it can trust or every reader learns the key codec (`Uuid7` byte order, variable-width string keys). One redundant column is cheaper than a shared codec.
- **Discovering the pairs from the rows.** A pair that disappears would leave its old table standing with stale rows, and a pair that first appears would race the reader's declaration.

## 5. Consequences

A property-graph declaration is now writable over a published lake with no transformation step, and it stays writable as the graph grows, because empty pair tables are published from the start. Nothing about the graph is persisted: the declaration is regenerated by whoever reads the lake, and the lake keeps only the tables it would keep anyway.
