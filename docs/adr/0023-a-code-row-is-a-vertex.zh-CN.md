# 0023 — 代码行是一个顶点

> **语言：** [English](0023-a-code-row-is-a-vertex.md)（主） · [中文](0023-a-code-row-is-a-vertex.zh-CN.md)

**状态：** 已接受并落地（2026-10-31）。门、闸与测试同批落地。
**日期：** 2026-10-31
**修订：** ADR-0012（代码仓的身份）。

## 背景

gravity ADR-0003 §3 说：完成是**调用点**写下的，永远不是模型的判断。所以派发一步之前，gravity 必须知道这一段代码关掉哪些未完成的任务。它要的绑定是一条事实——

```json
["run the migration", "task", {}, "finishes_on", {}, "code-7", "code", {}]
```

——而事实只够得着**顶点**。代码行并不是顶点：ADR-0012 给了它一个 ns 35 里的裸代理 id，只按数字寻址，别的什么都不认。于是这条绑定无处落脚，而绕开它的每一种办法，都是在跟地址空间讲价：

- **再加一种端点**（mem-core 的 `Endpoint::Code(u64)`）：为一个消费方的关系，让解析器、渲染器、删除路径和每一个解端点的读者都学会第三种词汇。
- **改绑到 skill**（skill 确实是顶点）：步序没地方放——多步脚本会因为在第 3 步做的功，在第 1 步就把任务关掉。
- **放到任务的状态表当字段**：给一张已有数据的表加列是静默的布局迁移，而且把关系降级成列。
- **新开第三张表**（`[scope][node_id] → code_id`）：这是 k10r 自己的写法，不用迁移，但等于给已经知道怎么装的东西再造一套平行地址空间。

四条都是在躲「把代码搬进图里」这件事。搬比它们都便宜，而且它把问题关掉，不是搁置。

## 决定

**1. 代码行就是普通顶点。** ns 36，`kind = "code"`，和其他所有节点同一个集合——任务和 skill 都在那里（ADR-0021、ADR-0015）。顶点名 `code-{id}`，`{id}` 就是 code id：图按名字寻址，调用方按数字寻址，名字除了这个数字不承载别的。

**2. `code_id` 不变。** skill 的 `steps[].code_id` 照旧装它，gravity 照旧按数字取，一行代码保持它被写入时的那个 id。变的只是这个数字住在哪儿：它现在长在一个节点上，所以事实够得着它。

**3. 载荷以版本链的形式搬到顶点旁边（ns 35，边表）。** 键 `[scope][code_id][rev]`：language、description、parameters、source。`rev` 从 1 起、只增不减，写下的版本永不覆盖——改一次脚本，是追加下一版。**在场即意义**——没有边表的节点不是代码——载荷不进顶点的 props，因为脚本源码不该是每个读实体表的人都要解的一段动态数据。id 分配仍是原来的水位：写过的最大 `code_id`，所以删掉的行不会把 id 腾出来复用。

用链而不是更简单的原地替换，是因为脚本会被修正，而**跑过的那一版**必须事后可读——审计（「那次调用拿到的是哪份正文」）、参照（「能用的那一版」）、以及落在某一次运行上的计数。脚本很小、改得不勤，链占的空间与它换来的东西比，是噪声。地址也不动：`code_id` 仍然是这个脚本，它的顶点仍然是事实指着的东西，所以一次改版之后 `task --finishes_on--> code`、按 id 引用它的 skill、以及所有计数**原地不动**。

**当前版本是这个脚本键段的最后一个键，从来不是指针。** 存一个「头」，等于给同一件事再存第二个事实，而它和行不一致的那天就是静默错误。键序不会跟自己不一致：一个脚本的各版本在键序里连续（定宽键字段），所以常规读 = 对**这个脚本**键段的段尾做一次反向 seek + 对落到的那一版做一次点读——不遍历历史，更不扫全表（okm 的类型化前缀 probe 配双向惰性扫描，ADR-0049；地址头由 Collection 拼，不由手写字节拼）。

**4. 门按 scope。** `POST /code/{scope}` 写入并回答 id；`GET /code/{scope}/{code_id}` 读当前版本，并在回答里带上它的 `rev`；`GET /code/{scope}/{code_id}/{rev}` 读指定版本，也就是审核用的那次读；`POST /code/{scope}/{code_id}/touch` 记录下面的使用计数（§7）。导出/导入把边表当作 `code` 表，和语料里其它表一起走。scope 不是装饰：顶点活在那个 scope 的图里，没有 scope 的代码行就是个无处安放的节点。

**5. 绑定在开启时声明，写成事实。**

```text
POST /tasks/{scope}  { "name": ..., "finishes_on": [code_id, ...] }
```

门为每个 code id 写一条 `finishes_on` 边——普通事实，不加动词、不加表。三条规矩要紧：

- 没交付过的 code id 按名字**拒掉**（400）。绑到空处是调用方的 bug，而造一个 `code-99` 幽灵顶点比报错更糟。
- 重复声明同一条绑定是幂等的（写入回答 `Bumped`），而且再开一次已存在的任务仍然不动它的状态——这才让后一轮能给自己上一轮开过的任务补绑定。
- 绑定只增不改。撤掉一条绑定是撤回一条边，没有门假装能做。

绑定指**脚本**，不指某一版：修正之前绑上的任务，跑的是修正后的脚本。这是本意——任务说的是「等这件事做完」，不是「等这些确切的字节跑完」——而钉住版本需要版本能被事实寻址，也就是下面被否掉的那个形态。某次运行到底拿到了什么仍然可回答：它读的版本在回答里（`rev`），那份不可变的正文在那个编号下永远可读。

**6. k10r 不关闭任何东西。** 列表对每个任务报出 `finishes_on: [code_id…]`（从边读出来，不存第二份），由 gravity 在那次成功的调用点关掉任务。仓负责回答，执行者负责写。

**7. 顶点带着使用计数。** 代码顶点带 `invoke_calls`、`invoke_ok`、`last_invoked`——与 ADR-0018 给技能节点的同一组声明字段——由 `POST /code/{scope}/{code_id}/touch` 记录：跑之前 `attempt`，跑完 `success`。

**为什么记在脚本上，不记在调用方。** 脚本不归跑它的东西所有：一条 `generate-pdf` 行可以是任意多个 skill 的步骤，派发它的工具也可能每次不同。记在调用方的数就必须再按脚本拆回去——而拆不回去：三个 skill 各跑过同一个脚本一次，留下的三个计数里没有"这个脚本跑了三次"这回事；反过来，脚本上的数也说不清是哪条路径调用的。两边都记，各记在自己的行上；互不派生，这不是冗余，是两个不同的问题（"这个流程被试过 N 次"／"这段代码跑了 N 次"）。

**为什么在顶点上，不另开一张表。** 这些字段本来就长在实体行上（ADR-0018 的修订），所以一次计数就是一次行写入，没有新 schema；而计数读者就是图——`tool_invoke_count` 与权重系统本来就按这些数排序，放在单独表里的计数，恰好对它是不可见的。

**一次 touch 不是什么。** 按契约是尽力而为：gravity 在跑旁边发一下、读一个回执，从不把它当前置条件。所以失败的一次跑留下 `calls > ok`，这正是读者要找的状态——而一次没能写进计数器的运行，仍然算跑过。

## 为什么不

- **`Endpoint::Code`**：见背景。新增一种端点是改图的地址空间，代价由所有读者分摊，换来的只是一条关系写得出来。
- **源码进顶点 props**：props 是读节点的人都解的东西；脚本是载荷，载荷进边表（ADR-0019 对向量边表的规矩，这里再用一次）。
- **有语义的 `name`**（描述转成的 slug）**：改名会断掉按名字指它的边，而数字本身已经是身份。
- **版本当顶点**（每个版本自成一个节点、版本之间加一条 `supersedes` 边、再用一条事实指明「当前」）：每个脚本多一个身份、每次修正多一条边、外加一个会说谎的头——正是本 ADR 拆掉的那套平行地址空间。版本是同一张表家族内部的簿记；图是用来装「东西之间的关系」的。

## 后果

- 实体表每行代码多一行，这一行出现在每一次图读取和每一份备份里。一个 bundle 的实体数是「事实的节点 + code 顶点」，读恢复报告时要知道这件事。
- `graph --code vertex` 从查表变成遍历：事实终于能说「哪段代码属于什么」，gravity Phase 5 的计数器（某步跑了多少次）也有了落脚处——落在真正跑过的那行代码上，不只在 skill 上。
- 一行代码是两次写入（先顶点、后第一版边表）。顺序是故意的：失败只会留下一个惰性节点，绝不会留下一张没人够得着的表。
- ADR-0012 主张「不具名的身份」的理由仍然成立——没有任何东西缓存名字，调用方每次调用都重读这一行——但名字现在由图给，是合成出来、由 id 推出来的，不是调用方提议的字段。
