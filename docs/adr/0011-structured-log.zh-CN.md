# ADR-0011: 结构化日志——程序内部状态作为可丢的诊断行

**状态**：设计定案（实现待排期；ns 41 已声明，尚无代码）
**日期**：2026-10-20
**英文版**：[0011-structured-log.md](0011-structured-log.md)
**相关**：ADR-0008（压缩判词，§4 的「不预支训练集」）、ADR-0007（core / analysis 两个 API 类不混）、ADR-0002（一张表一个 ns）

## 背景

k10r 里有一类数据既不是知识、也不是会话：压缩为什么在那个点切、检索索引何时重建、引擎报了什么错。它们没有领域身份——不是实体、不是边、不是消息——所以不该进图，也不该进 channel 日志（那是用户可见的会话内容）。但它们**不确定却可能有用**：今天是为了调试，将来可能是调参的样本。

先前的写法是给每类记录各建一张表，决策日志（曾占 ns 40）就是这么来的，后来被撤除：它为「将来拟合调参」预支了一张表，而标签不存在、读者不存在；真正必须回答的问题（「这一段被压到哪儿」）由 checkpoint 的指针行自己回答。撤除是对的，但结论被推得太远了一步——**内部状态确实需要一处落脚点**，只是它不该是「每种记录一张表」，也不该假装马上会被训练。

## 决策

### 1. 一张表，键是时间

ns 41，表名 `log`，只追加，键 `[ts_ms 8B][seq 8B]`（BE 定宽，字节序即时间序，回调/区间扫都是前缀扫）。

- `ts_ms` 是 **k10r 自己的钟**：这张表的写者就是进程本身，不存在 ADR-0008 §3「调用方持钟」的问题——那条规矩属于调用方提供的业务数据，不属于进程自己的观察。
- `seq` 是进程内的单调计数（`u64`），开库时从表的最后一个键续上（与既有表恢复 id 的那套做法一致），所以重启不会撞号。同一毫秒内的多条由此分开；跨进程不可能同时写（Fjall 的目录锁保证单写者）。
- 没有 scope、没有 channel 进键：这是程序的内部状态，不是某个用户的记忆。要按 channel / scope 找，靠行里的定位字段（§3），那是一次扫描——有界表上的扫描本来就便宜。

### 2. 固定的是低基数的那几样，且「声明」不等于「索引」

- `level u8`：trace / debug / info / warn / error，常量模块给值（`level::WARN` 这类），不让调用点自己写数字。
- `event Vocab<u16>`：事件名，走常量词汇表（`event::COMPRESSION_VERDICT` 等），盘上两个字节——打字错误在调用点上就是编译错误，同一个事件也不会有三种拼法。
- `source Vocab<u16>` 与 `note Str`（§8）：这行从哪个模块/访问路径来，以及唯一那个自由文本字段（给字段说不清的行用）。
- 四个都是**声明字段**（热段、编码固定），但**都不挂 0x1 面**：面是「值 → pkey」的实体条目，每行多一条就是每次写多一次索引写，而这张表有界、按时间扫一遍不贵。等某个查询真成了热路径再加面——与 ADR-0005 撤掉三个未被扫描的面是同一条纪律。

OKM 的对应物，别记混：没有「低基数类型」这种东西。低基数字段的做法是声明字段（U8..U64 / FixedBytes / Str）可选地挂面；低基数**集合**才是 func 多值索引（元素 → pkey）或高基数时退到应用层 bloom；`#[ok_nodes(Table, …)]` 给节点集合定类型（枚举由列出的表生成），不是字段类型。

### 3. 变的进动态段：定位 + 载荷

槽 1 的动态段承载开放词汇（UInt / Int / F64 / Str / Bool / Bytes / Array / Obj / Null），名字任意：

- **定位**：`channel` / `scope` / `entity` / `edge` / `msg`——哪一个适用就记哪一个，名字取自固定词汇表，值用既有的键类型（u64 / 复合键字段）。拿不到就不写，不造占位。
- **载荷**：参数快照、三个信号的实测值、切分点、错误原文、耗时。嵌套对象必须走 `put_frame_named`（裸 `put_frame` 没有字典可解析名字）。

### 4. 什么进、什么不进

进：**不在核心业务路径上**的决策与状态变化——压缩判词及其整份参数/信号快照（这就是撤掉决策日志后那份训练样本的新家：它今天就有读者，调试引擎时要看）、索引重建与淘汰、引擎级错误、容量裁剪之外的维护动作。

不进：消息内容、用户数据、任何领域行已经持有的东西；不在热路径上逐调用打点。判断标准不是「有没有用」，而是「出问题时会不会想回看这一条」。

k10r 不对日志行做任何动作：level 不是策略，不触发告警、不改变行为。它只是让一次扫描能先看 errors。

### 5. 表是有界的，裁剪在写侧

这张表会无限长，而它承载的东西可丢。`krystallizer.kdl` 的 `logs { max-rows }` 给上限；写一行时在**同一个 batch** 里从最老的键开始删到限额内。

裁剪本身**不记日志**——否则裁剪产生日志、日志触发裁剪，自激。丢弃是明确接受的代价：这是一张诊断表，不是账本。

### 6. 不开 HTTP 门

它不在两个接口面上（ADR-0001 的 session / memory / task），也不属于 core API（ADR-0007）。等真有查看器或分析脚本时，它按 **analysis 类**开门——那一类的形状可以随分析需求漂移，永远不进模型的工具列表，也永远不是回合循环的依赖。

### 7. 第一个写者：压缩判词

压缩判词正是这张表存在的理由——一个决策、触发它的信号、它指定的切分点、以及据以判断的数字，在决策日志撤除之后无处可放（ADR-0008）。`LogStore::record_verdict` 写的就是这一行：`channel`、`split_ts` + `split_sub`（指针的两半）、`trigger` 用**词**（`budget` / `cache_clock` / `both`——日志是给人读的，没人记得住的编码不算记录）、`assembled_bytes`，以及真正触发的信号。没触发的信号不写字段：缺失不能读成零，这正是「缓存钟沉默」与「它说是 0」的区别。

读侧是窗口，不是查询语言：`since(ts_ms)` 返回下界之后的全部行，按键序（字节序本来就给定了），`max_rows` 保证它永远有界。

### 8. 字段形状（已裁决）

`ts_ms u64` 是键。声明字段共四个，其余全部走动态段：

- `level u8`——五个值，有序，代码里比较。
- `event Vocab<u16>`——内存里是标签，盘上是 2 字节 id（okm ADR-0032）。
- `source Vocab<u16>`——写下这一行的模块或访问路径；`0` = 无。
- `note Str`——**唯一**的自由文本字段：一句给人看的话，不是载荷。载荷属于动态段，用
  它自己的名字。

`event` 与 `source` 用 Vocab，因为它们是一个**封闭、小、无限重复**的集合——词汇表正是为
这个形状存在的。`String` 会在每一行上重花同样的字节，还允许同一种事件有三种拼法；
2 字节的 id 拼不错，而且拼错会变成调用点上的编译错误，而不是一撮谁都没法 group 的行。
`note` 反过来留在字符串，因为它是唯一一个内容不是名字的字段。`level` 留在 `u8`，因为它是
代码要比较的一小块有序域，不是要打印的标签。

状态：2026-10-20 **已落地**。真正的改动只是行上的**字段类型**。内化是类型自己的
事——行类型声明了 `Vocab` 字段时，okm 的写路径自己内化（`Collection::put` 克隆文档后跑
`__okm_intern`），读路径自己把标签解回来（`get` 跑 `__okm_deref_vocab`），所以 k10r 的 store
和门都不分配、也不查表。`append` 仍然收 `&str`，内部做 `Vocab::of(event)`，调用点一行不改。
唯一诚实的代价：声明了 Vocab 字段的表每次写多一次文档克隆（`put(&R)` 不可变签名的价钱）。
断代是一次干净的断代（预生产，ADR-0018——不迁移）。它只等了一件事：krystallizer 钉住的
okm rev 早于 Vocab 文档字段，lock 从 `e0842a7` 挪到 `49c7406` 之后，行就按裁决的样子编过了。
`LogStore::row(key)` 返回声明字段，读 level 不必走动态 map。见 PLAN 2.9c。

## Why Not

- **每种记录一张表（决策日志的形态）**：每冒出一个新问题就要一次 schema 变更，而它们共享同一件事——「不确定但可能有用」。一表加动态段把这件事收敛成一次决定。
- **把内部状态写进 channel 日志或图**：channel 日志属于会话（用户可见内容），图属于知识（有实体身份）。内部状态两处都不属于；混进去会让压缩、检索、消费者看见本该被忽略的字节。
- **给 level / event 挂 0x1 面**：每行多一次索引写，换来一个当前没人发的查询。不预支。
- **只依赖进程日志（stderr / tracing）**：服务化之后进程日志随容器或终端消失，而「那次压缩为什么这样切」要能在事后从库里捞出来。tracing 留给运维，分析需要的字节落库。
- **无界增长 + TTL 守护**：多一个常驻机制、多一处可能失效的地方；写侧裁剪是同一 batch 里的几行删除，没有第二种生命周期。
- **给日志表定领域词汇（压缩 / 检索 / 图各自一张）**：那就回到「每种记录一张表」。事件名是词汇表，不是 schema。

## 后果

- ns 41 = `log`；ns 40 仍空（决策日志撤除后未再占用）。
- `logs { max-rows }` 作为新子系统节点进 `krystallizer.kdl`（统一配置文件加节点，不加文件）。
- 压缩判词从「只随投影返回」变成「随投影返回 + 落一行」：ADR-0008 §4 的「不预支训练集」仍然成立——这一行先服务调试，调参只是它顺带的可能用途，且不需要新表。
- 不动任何消费者契约：没有门、没有签名变化，gravity / prism / booth 一律感知不到它。
- 观察自身有限度：日志表里的行数与裁剪动作都不是可观测对象（裁剪不记自身），所以「丢了哪些」只能由配置上限推知——这是刻意的，避免自激与递归的容量问题。
