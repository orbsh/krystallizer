# 0024 — 轮次是消息键的一个轴，而号由存储来发

> **Languages:** [English](0024-the-turn-is-a-key-axis.md) (primary) · [中文](0024-the-turn-is-a-key-axis.zh-CN.md)

**Status:** Accepted (2026-10-31)，已落在 mem-core 与 HTTP 面：键、两道门（`/channels/{c}/turns`、`…/turns/{t}/close`）、投影跳过未关闭轮次、checkpoint 带轮次。下一步是 gravity 的逐轮写入。
**Date:** 2026-10-31

## Context

`MessageKey` 是 `[channel_id][ts_ms][sub]`（ADR-0008 §3），这个选择是为读做的：字节序就是 `(ts, sub)` 序，所以回放、增量、最大间隔读都是一次按日志自身排序的前缀扫描——不排序、不加二级索引。键里没有"轮次"这个东西，是因为当时不需要：一轮在结束时一次性写下自己的行，唯一的读者是下一轮的读。

三件事把它拆开了。

**1. 一轮的行必须在它结束之前就存在。** `human` 类调用可能跑几分钟，派发它的入口可能被挂起再恢复（aura 的冷层）。恢复的轮次需要拿回自己的工作集——问题、已经跑过的轮次、还悬着的东西。只在整轮成功时才落下这一轮，等于没有可恢复的东西。

**2. 可以同时有多轮开着。** 一旦允许用户插话、一旦有挂起的轮次在等结果，一个频道里就有不止一轮在飞。这时时间本身圈不出一轮：两个开着的轮次的行会交错，"ts X 之后的全部"不再等于"这一轮"。

**3. 轮次必须能被精确地压缩。** 逐轮写意味着已完成轮次的行要被收敛成净效应（每个成功调用一行，即 gravity 今天的形状）。按时间范围做的压缩会误删邻居的行；按轮次做的不会。

## Decision

### 1. 键带上轮次：`[channel_id][turn_id][ts_ms][sub]`

全部定宽、BE——于是一轮是一个连续的前缀区间，区间内 `(ts, sub)` 序就是字节序。压缩一轮是一次前缀扫描；读一轮是一次前缀扫描；不需要任何新索引。

读语义随之改变，这是要大声写出来的部分：**键序是轮次的创建顺序，再加轮内时间序——它不是全局时间序。** 一个被挂起一小时的轮次恢复时用的还是原来的 id，但 `ts_ms` 是新的，于是它的段落在睡眠期间创建的那些轮次之前，而它的行却更新。任何要严格时间序的视图，必须按行的 `ts_ms` 归并轮次段。对于带挂起和插话的对话，这个归并就是诚实的重建方式，不是权宜之计。

### 2. `turn_id` 由**存储**按频道发号，在轮次开始的时候

不由调用方发。调用方的计数器会在多端之间撞、在重试之间撞、在同一客户端开的两个轮次之间撞；存储手里那一个计数器本来就不会。

发号发生在轮次的**第一次写入**。轮次存在是因为用户说了话：承载那句话的行与发号是同一次调用，存储在其中读 `last_turn + 1`——那一刻上一个轮次已经在日志里，日志就是发号所需的全部证据。于是同一频道同时开出的两个轮次不可能拿到同一个号（它们是两次写，由存储串行），而在写第一行之前就被放弃的轮次什么都不消耗：日志只会出现空洞，不会出现重复。第一行写入的应答带回这个号，这一轮后续每一行都在它下面写。

### 3. 每一轮都立即写

模型要工具、调用跑完、这一轮的行落地——每轮一次写，而不是最后一次性写。这是可恢复的来源，也是"轮次在飞时它的行就已可见"的来源。代价是被放弃的轮次会留下行，见 §5。

### 4. 收尾用**一条**显式类型的记录

循环结束、答案完整时，写入方把最终完整输出提交一次，`kind = FINAL`（行词表里的一个新码；写入方照旧只写码，标签留在这里），并在**同一次提交**里带上要保留的 sub——问题、净效应工具行、答案。

### 5. k10r 收到终稿后自己压缩这一轮

不开 HTTP 面、不要求调用方配合：遇到 `FINAL` 写入时，k10r 前缀扫描这一轮，留下记录点名要留的 sub，其余 `Collection::purge`（队列压缩早就在用的原语）。一次扫描、一轮的行、每轮一次。保留清单是显式数据而不是从 role/kind 推断出来的——"哪些行是多余的"是写入方的判断，在这里猜就等于多养一条要同步的规则。

### 6. 开着的轮次被标记，投影跳过它们

有开启记录、没有 `FINAL` 的轮次就是 OPEN：它的行是工作状态，不是历史。投影标出这一段，并把它排除在模型的视图之外。多个挂起轮次能同时成立也是靠这条——插话不需要任何特殊处理，因为每个开着的轮次本来就是自己的段。

### 7. checkpoint 的指针带轮次，键也带

一条 checkpoint 行说它的摘要覆盖到哪条日志记录，而到目前为止**键就是指针**
（`[channel][ts_ms][sub]`，ADR-0008 §4）：一个地址，没有第二个字段要同步。轮次轴把
这种同一性打破了，修法是把轮次放进**两个地方**：

- `sub` 只在**一轮内部**破平手，所以一旦两轮可以同时开着，`(ts_ms, sub)` 在整个频道里
  就不再唯一。而且两轮完全可能在同一毫秒写下同一个 `sub`——不是稀奇事：一个写者、一口钟、
  同一毫秒里开出的两轮——那么 `(ts_ms, sub)` 形状的键会让后一次压缩**覆盖**前一次。
- 所以指针是 `(turn_id, ts_ms, sub)`：日志自己键空间里的一个地址，也正是增量"严格在其
  之后"读的那个空间；checkpoint 的键是 `[channel][turn_id][ts_ms][sub]`。

沿覆盖轴看，键序是单调的，因为一次压缩永远覆盖上一个节点**之后**的那一段——它摘要的
增量就上一次摘要结束的地方开始。于是"最新节点 = 键最大"依然成立，而且现在成立的理由
是对的：键是日志位置，不是那次压缩发起的墙上时间。（按时间锚定从来不是必需的：被挂起
一小时的轮次压缩得晚，但它压的仍是上一次覆盖之后的尾部，所以不管钟说什么，它的指针都比
那次覆盖大。）

行里另外还带一个轮次字段 `suggested_turn_id`，那是**本可以**选的那个切点——一个标签，
不是覆盖点。

### 8. 压缩永远不可能指向一个会被压缩的集合

尾部操作的范围只在**已关闭**的轮次上计算：压缩覆盖 `(coverage, verified checkpoint]`，而开着的轮次按构造就在所有 checkpoint 之后——它没有 `FINAL`，所以没有任何指针能点到它；而 collapse 只删刚刚关闭的那一轮里的行。让删除安全的不变式就是这一条，它必须写在计算范围的地方，而不只是写在这里。

## Consequences

- **时间序是一次归并，不是一次扫描。** 任何要全局顺序的读者（拼 transcript 的视图、翻历史的 UI）按行的 `ts_ms` 或按开启记录的时间戳给轮次段排序。这是对几个段的额外一步排序，不是对整个日志排序。
- **日志变得可变了——只在一个已关闭的轮次内部。** 别的地方永远不清，删除集合被一轮已经结束的范围框住，checkpoint 的范围从不覆盖它。
- **被放弃的轮次是永久的，除非定一条策略。** 入口死掉的开轮会一直留着它的行，被投影永远跳过。
- **增量的边界仍然是 checkpoint，不是轮次**：轮次是写入与删除的单位，checkpoint 是读的切点。两者是不同的轴，代码不许混。
- **`sub` 的含义不变**（同一毫秒内的次序，单一写入方），但它不再是频道内唯一的排序依据。

## Not decided here

- **开轮次的保留。** 崩溃的轮次留下的行会一直待到有人清扫。存储是在下一轮开启时扫、按时钟扫、还是永不扫，这条记录不选。
- **`FINAL` 是否还携带本轮元数据**（模型、mount 表、耗时），还是只有答案行加一份保留清单。
- **id 的宽度与耗尽。** 每频道 `u64` 是暂定假设，还没有东西依赖它。
