# ADR-0008: 统一 channel 日志——agent 上下文是投影，启发式压缩

**状态**：部分落地（2026-10-09：最小切片——channel 消息 ns 33 + checkpoint ns 34，`ChannelStore::append`/`fetch_full`/`append_checkpoint`，服务 gravity Phase 0；2026-10-20：压缩策略引擎（§4）；同日两条裁决：checkpoint 是 **channel 的指针**（键里没有成员段），压缩状态**只有 checkpoint 一张表**——初始提示词快照随行，不另立决策日志；待办：thread、topic tag、members，以及代码侧把恒为 1 的成员段去掉、把决策日志并入 checkpoint）
**日期**：2026-09-22
**英文版**：[0008-unified-channel-log.md](0008-unified-channel-log.md)
**修订**：ADR-0001（summarize 的截断步骤）、ADR-0002（session 消息键）、ADR-0006（session 读写形态）

## 背景

ADR-0001 在 agent 私有的 session 文档上定义了会话控制
（branch/tail/summarize），ADR-0002 把 session 消息键定为
`(ns, user_id, session_id, seq)`。两种消费形态被留成了两个容器：

1. **人的聊天**——多人 channel、私聊（两成员 channel）、已读游标、
   锚在消息上的 thread、话题标签。
2. **LLM 对话**——agent 的上下文窗口、长度控制（压缩）、与主动
   记忆提取的配合。

两者消费的是同一个底层对象——有序消息日志——但草案把它们
建成了两个容器。这意味着「拉增量」「压缩」「已读」各实现两遍，
而两套实现的差异（coverage 对未读游标、checkpoint 对历史）恰好
都是投影层能吸收的。

同一区域还暴露了第二个缺陷：ADR-0002 以「同一毫秒的两条消息不能
乱序」为由拒绝墙钟时间戳、采用每 session 单调 seq。该理由只考虑了
跨发送方乱序，漏掉了反向风险——共享计数器分配的 seq 与因果无关，
而回复的时间戳必然晚于它所回复的消息（回复方必须先看到它）。

## 决策

### 1. 唯一容器：channel 日志

人的聊天与 LLM 对话共享同一个存储原语：**append-only 的 channel
日志**，键 `(ns, channel_id, timestamp)`。除此之外没有第二个容器。

- 私聊 = 两成员 channel。群聊 = N 成员 channel（成员是**发送者**，
  见 §5 与 ADR-0009）。
- agent 的「session」不是容器，是**这道 channel 的投影**：channel 的
  checkpoint（指针 + 摘要）+ 指针之后的增量。
- thread 是锚在 `(channel_id, timestamp)` 上的子 channel——同一张
  messages 表加 parent 指针，公开的第二维度。它不是 agent 的分支。
- 话题标签是消息行上的**二级索引**（OKM index entry；标签树沿用
  既有的 tag-tree 设计），不是第三种容器。论坛式消费（按主题拉取）
  与 IM 式消费（按时间跟随）是同一份日志上的两条读路径。

### 2. agent 的上下文是投影

agent 从不拥有、截断、改写日志。它的上下文在读取时组装。目的只有一个：
让对话接着走下去，而不必管理上下文长度——真正需要跨会话记住的东西交给
长期记忆（图，主动面），上下文这一侧只留「一段摘要 + 初始提示词 + 最近
几条原文」。checkpoint 就是这道接缝的载体：它记录「日志的哪一条之前已经
被压成一段话」。

```text
channel:  [m1][m2][m3][m4][m5][m6][m7]...
                        ^
checkpoint: 指针 → m4；内容 = 摘要(m1..m4) + 当时的初始提示词快照
投影:      [初始提示词快照][摘要] + [m5][m6][m7]
```

- **压缩是追加，永不截断。** summarize = 经 tail（ADR-0001 的单回合
  分支）跑摘要 → 落一条 checkpoint（指针 + 摘要文本）→ 投影此后读
  最新 checkpoint + 指针之后的增量。日志本身永不收缩；摘要错了可以重跑，
  历史可以随时重新分割重压。这打破了「压缩必须吞下全部历史」的定势：
  每次压缩覆盖有界的一段，摘要质量有界。
- **接缝是软的，不是硬切分。** 摘要由尾提示词（§4）要求写成「读完这段
  就能接着做」的形态——它是前面那段的自述，不是一份提纲，所以切点两侧
  读起来是连续的。这是它比硬切分体验更好的原因：接缝处让掉的是修辞和
  重复，不是事实、决定与未决问题。正因为是软接缝，边界上的小误差不致命
  （重复压一段、或晚压一轮，代价都是一次模型调用，不是上下文断裂）。
- **压缩点立在日志旁边，不在日志之内。** checkpoint 住在**自己的表**
  （ns 34）里，用指针指向日志——它的可变性从不碰到日志的任何一行。
  追加优先（ADR-0002）覆盖的是图与数据面，不适用于日志——日志无例外地
  只追加。
- **checkpoint 是 channel 的指针，表按指针键控**（`[channel][ts_ms][sub]`）。
  行里三样：指针所指那一段的**摘要**、那次压缩时的**初始提示词快照**、
  以及「还没有摘要」这个状态（正在压）。读投影 = 找键序最大的、带摘要的
  那一行，从它指到的那条记录之后截取增量。指针要指到**一条记录**而不是
  一个毫秒：覆盖点必须能说清「从哪一条之后还是原文」，而同一毫秒里可以有
  多条（§3 的 `sub` 正是为此存在）；只记 `ts_ms` 时，同毫秒里排在切点之后
  的记录会同时掉出增量与摘要，静默丢消息。
- **初始提示词随 checkpoint 存快照，不在每次读取时重算。** 人设/风格是从
  图遍历装配出来的，这一轮的记忆添加可能改掉它——每次重算就每次可能变，
  而 prompt cache 的前提是**前缀字节稳定**：头部一抖动，整段上下文重新
  计价，压缩省下的钱又还回去了。所以快照在压缩那一刻生成并随 checkpoint
  存下，下次压缩之前头部都用这份快照。代价是人设更新滞后到下一次压缩
  ——这是拿新鲜度换缓存稳定，取的是后者。
- **行可以有很多，读只取最新的。** 重复压缩（同一段被压两次）各写一行，
  指向同一个节点，读出来结果相同——幂等，代价是一次多余的模型调用，可以
  接受。晚到的摘要落在更早的指针上时，它排在最大行之下，读路径看不见它，
  但**不必删**：那是免费的历史（哪一次压过哪一段），删它反而要多一次写。
  上传/返回的顺序不做任何仲裁——不做「谁先谁后」的锁。
- **正在压的标记就是「有一行还没有摘要」。** 引擎看到比当前覆盖点新却没
  摘要的行，就不再提议（下一次读取直接放过）。没有这个标记也能跑——同时
  发生的压缩与对话里，压缩通常更快——它存在的意义只是少浪费一次请求。
- **键里没有成员维度。** 一条 channel 只有一道声音（§3「同一时刻只有一个
  写者」是同一件事的另一种说法），同一份日志上不存在第二个压缩主体；而
  agent 也不是固定身份的持有者——它的边界随长期记忆流动，压缩之后头部就
  跟着换（k10r 的初始目标之一就是服务液态化组织）。多出来的那一键段只能
  是一段恒量，而恒量不是维度。
- **组装是有序的，从头开始**：初始提示词快照（人设 / 风格——初始化记忆，
  ADR-0001）→ 压缩点 → 压缩点之后的消息。快照占据的正是摘要以前独占的
  头部位置，因为它是走被动通道的长期内容；增量按 key 序跟在后面。组装仍是
  k10r 的内部细节——调用方收到投影，从不自己组装；而且头部是**渲染好的
  文本**（ADR-0010 §5 的 `format` 参数）：调用方把那段文本原样注入，绝不
  自己装配头部的事实列表。
- **已读游标也是 channel 的指针**（`ts_ms + sub`，同样指向一条记录）。
  它只在多方（含双人）才需要：那时「读到哪」因人而异，是每个参与者自己的
  事实，游标随 members 表（ADR-0009 / Phase 2.7）才带上人的维度。单人与
  agent 的形态里可以安全地假设游标永远是最新的——agent 每轮都读，日志最后
  一条就是它读到的位置，于是不必存；缓存钟的空闲时长直接由「现在 − 日志
  最后一条的 ts」得出。

本条修订 ADR-0006：「fetch 全量 session、写回 session」改为
「append 自己的记录、读自己的投影」。无状态循环的性质不变——
持久化与组装仍然沉入存储层，变的只是读写形态；循环依旧不改写
历史，且现在存储层从结构上禁止它这么做。

### 3. 时间戳定序（修订 ADR-0002 的 seq）

消息排序用 **gravity 写入时打的时间戳**，不用单调计数器。

- **免费拿到因果一致**：回复必然晚于它所回答的消息（回复方先看到
  它），物理时钟给出与因果偏序一致的全序——带真实时钟的 Lamport
  clock 论证。共享 seq 计数器没有这个性质：回复可能落在它逻辑上
  跟随的并发消息之间。
- **跨发送方乱序无害**：两条无因果关系的消息是并发的，相对顺序
  不改变任何语义。
- **单一时钟权威**：gravity 的时钟就是 channel 的时间。对话流跑在
  内部时间上；用户客户端的时钟从不参与定序（客户端时间戳至多是
  展示元数据）。这消除了多方时钟偏移问题：只有 gravity 的时钟需要
  正常，而偏移不可能破坏因果——回复永远在它所回答的消息写入之后
  才写入。
- **同毫秒突发**（gravity 同时服务多用户/多 channel）：键追加决胜段
  `sub`（`u16`，写者在同一毫秒内的顺序计数）。用写者自己的计数做决胜段，
  前提是**同一 channel 同一时刻只有一个写者**：一个 channel 的 gravity 实例
  独占它的时钟（见下），所以同一 channel 的两次追加是顺序的；`u16` 在
  一毫秒 65 536 条时溢出，是病态信号，不是需要重新设计键的理由。落地键是
  `[channel_id 8B][ts_ms 8B][sub 2B]`（见 MODELING，hex 测试锁定）；写者段
  在"一个 channel 多个写者"的情形下被考虑过，但不进键——本 ADR 定义的形态
  里不存在这种情形。
- **max-gap 变成时间差**：时间即序之后，最大间隙就是一次 range
  scan 里相邻条目的最大时间差——不需要第二索引，不需要 seq→时间
  反查。
- 存储成本净省：事件本来就该带时间戳，独立的 seq 列消失。

### 4. 压缩是参数化的策略引擎

压缩触发是启发式的，绝不用 LLM 判断：用 LLM 判断「话题是否转换」
花一次推理，判断完还得再花一次摘要——两次模型调用买一次机会。
分界点必须是零成本的。启发式如下：

- **缓存时钟触发**：prompt cache 的 TTL 快到期时（如 1 小时缓存的
  第 50 分钟空闲）且上下文有分量（超过下限百分比）→ 压缩——缓存
  反正要失效，压缩零成本。上下文只有几条、不到下限 → 不压；时钟
  是免费信号，不是义务。
- **预算触发**：到中段阈值（如上下文的 50%，而非 90%——阶梯定价
  低档便宜得多，且压缩质量随跨度增长而劣化；早压让每次摘要小而好）。
- **max-gap 分界**：在 coverage 头之前的有界窗口内，取相邻消息
  时间差最大处切开——对话停顿是话题转换的可观测痕迹，零模型成本。
  触发与分界要互相印证：若 max-gap 恰是当前的沉默（触发触发的那个
  空闲本身），不压。

**所有阈值是参数，不是常数。** 策略配置（`krystallizer.kdl` 的全局
默认）持有每一个数字：缓存比例、预算百分比、窗口边界、最小上下文
下限。每用户覆盖是预留的第二层（查一个覆盖表，miss 落到全局默认）
——结构上现在就预留，数值将来手动或自动填。

**不预支训练集。** 回归拟合需要标签（「这次压缩好不好」），标签不存在，
没有标签的拟合拟合的是噪音；而「哪一段被压了」这个必须回答的问题，答案
就在 checkpoint 自己的行里（指针 + 有没有摘要）。所以**不另立决策日志表**：
参数快照、触发信号值、分界位置的记录，等真有调参需求、真有标签时再加，
那时它是一张新表，而不是今天先付的存储与写入。压缩的判词随投影出行，
只服务当下这一次机会；判词与三个信号的实测值同时落一行结构化日志
（ADR-0011，那张表本来就有调试读者）。

**引擎的输入全在 k10r 自己手里，裁决随投影一起返回。** agent 侧不存在
压缩接口——调用方没有「请求压缩」的门，判断也不归调用方。信号就是
k10r 持有的那些：增量的时间戳（max-gap）、组装后上下文的体量（预算
百分比与下限）、以及这道 channel 的读位置（缓存钟：prompt cache 空闲的
时刻，正是这份投影没有被读的时刻）。读位置在单人与 agent 的形态里由
「日志最后一条」直接给出（§2），多方才有游标行。所以评估点落在**投影
读取**那一刻：引擎在组装产出时顺带跑完，裁决跟组装一起返回，不走第二次
调用。

**压缩点可以落在日志中段，裁决是一个控制字段，永不做成记录上的标记。**
压缩点就是启发式选出的分界，不是尾部；它之前的部分才是被压的。它跟在
调用方收到的记录旁边——投影上的一个控制字段，形态一次定成「对话与
控制并列」的对象（`{ records: [...], compress: { checkpoint: 30,
prompt: "…" } }`）：把注解抹进日志行既乱，又没给同一个字段本来要服务的
其它尾提示词/控制用途留位置；一个结构化字段能全部吸收，且不必重写记录
的形态。尾提示词的**文本**随该字段下发，所以它是 k10r 声明的产物
（PROMPTS），不是调用方自己编的。

**压缩那一趟是第二条分支，coverage 仍是 k10r 自己的算术。** 拿到指令后，
调用方额外跑一个 turn——压缩点之前的记录加上尾提示词——带外执行，作为
用户那一轮旁边的分支：用户的交互不等它，也看不见它。那个 turn 的回答
就是摘要，走普通追加路径回来；压缩点由 k10r 取被压那段的最后一条记录，
调用方从不自己声明 coverage。这是 §2「经 tail（单回合分支）」的具体写法，
不是第二个机制。

**2026-10-20 落地。** 引擎是 `mem-core/src/compress.rs`：纯函数，不调 LLM、
不定时，判词形状就是上一段声明的那一个。数值是 `krystallizer.kdl` 的
`compression { context-bytes budget-percent cache-ttl-ms floor-bytes }`；
`cache-ttl-ms` 是**开火点**，设在真实 TTL 之下（上面那个「1 小时缓存里
空转 50 分钟」的例子说的正是这件事），并且有测试断言文件里的数值等于
`Params::default()`。门是 `GET …/session?ts_ms=`：空闲时长按 §2 的读位置量
（单人形态即日志最后一条），然后才盖新的读位置——读取是缓存钟唯一的
可观测物，所以顺序就是信号本身——不给钟就照常出答案、什么也不盖（与
recall 的「无钟不计」同一条规矩）。引擎的状态落在 checkpoint 表自己身上
（§2 的指针行），不外加一张日志。

代码现状与本节有两处差距，去差距是这次裁决的落地件：三张表里 checkpoint /
cursor / 决策日志的键还带着恒为 1 的 `member` 段（`DEFAULT_MEMBER`），
checkpoint 的覆盖点还只有一个 `coverage_ts` 而没有 `sub`，决策日志（ns 40）
也仍然独立存在。目标形态：checkpoint 按 `[channel][ts][sub]` 键控、行里带
摘要与初始提示词快照，cursor 只在多方有行，决策日志表撤除。

**checkpoint 门只收摘要（2026-10-20）。** 调用方从不声明覆盖点：
`POST …/checkpoint` 的正文是 `{ summary }`，k10r 把它填在自己开出的那一行
上（指针就是当初交付的切分点；没有开着的行时是 400）——没有可填的行，
凭空造一个覆盖点就是让这边去猜本该它自己拥有的东西。消费方那一半同批动了：
gravity 的 `SessionProjection.compress` 把判词在两个 surface 上都带过去，
缝两头都闭上了；跑分支轮是 gravity Phase 3 的事。

### 5. 与记忆添加的分工

两者消费同一份日志；服务不同层，不合并：

- **summarize** 服务上下文：有损，为模型的工作集，受回合内延迟预算
  约束。
- **记忆添加**服务跨会话记忆：原子事实进图——由模型**自己的主动记忆
  添加**产生（调用方把那次工具调用接到 `ingest(fact)`），从不靠压缩的
  那一趟。不存在也不排程滞后的提取 worker。日志只追加意味着调用方
  **可以**滞后、批量、重跑同一份字节——那是一个可用性质，不是机制。
  所以 summarize 不再把关记忆添加：摘要服务上下文，主动添加服务跨会话
  记忆，没有谁规定它们得是同一次。

分开的根因：质量/延迟预算不同（摘要在回合内，事实的生产者是推理的那一方）；
而且压缩是「把这一段换成一段话」，记忆添加是「把这一次说清的事拆成一条条
可检索的事实」——前者服务连贯，后者服务召回。

**多方参与**——成员身份（members 表的显示名/角色，归属在序列化时
施加）、画像知识（关于某个成员的一组图事实——成员节点 + 它的类型标签
与边；没有 `kind=profile` 这个 flat 类别，ADR-0009）、插话策略（同一个策略
引擎的秒级被动触发）——由 ADR-0009 规定。成员是**发送者**的维度，进的是
消息行的字段与序列化的归属，不进 checkpoint 的键：单人形态不需要任何新增
机制，一条 channel 一道声音，所有触发挂在回合边界。沉默的决定**不落记录**
——没有决策日志表，等真有调参需求时再谈记什么。

## Why Not

- **session 作为第二容器（LLM 对话专用保留）**：拉增量、压缩、
  已读各实现两遍；差异（coverage 对游标、checkpoint 对历史）全部
  能被投影层吸收。拒绝。
- **LLM 判断话题边界**：一次判断 + 一次摘要 = 每次压缩两次调用；
  启发式（最大时间差）零成本且与触发互相印证。LLM 判断只有在它
  连摘要一起替代时才划算——那是「当场压缩」，恰是触发条件要避免的
  形态。作为分界机制拒绝。
- **截断式压缩（主流形态）**：毁掉重跑能力。截断日志上的坏摘要
  是永久的；append-only 日志上它是一次重试。拒绝。
- **按成员键控 checkpoint（旧草案）**：立论是「两个 agent 挂同一
  channel 各压一份」。那个场景不存在——agent 的边界随长期记忆流动，没有
  固定身份可做键；同一 channel 也只有一道声音。键里多一段恒量只会让每张
  表都多一个说不清含义的字段。拒绝。**游标是另一回事**：它记的是「谁读到
  哪」，多方（含双人）才有意义，所以键里保留成员段（§2）。
- **单独的决策日志表（含参数快照与信号值）**：它服务的是「将来拟合调参」，
  而标签不存在，所以那份记录今天没有任何读者；同时「这一段被压到哪儿」
  这个真问题由 checkpoint 的指针行自己回答。表被撤除，需要时再加。
- **每次读取重算初始提示词**：字节不稳 → prompt cache 每次失效，压缩省下
  的钱还回去。快照随 checkpoint 存。
- **现在就拟合策略参数**：标签尚不存在，拟合会追着噪音跑。记录什么、记在
  哪，等标签真出现时再定——那时它是新表，不是今天先付的存储。

## 后果

- ADR-0002 的消息键 `(ns, user_id, session_id, seq)` 被
  `(ns, channel_id, timestamp+决胜段)` 取代；session_id 从键空间
  消失——统一落在这里。
- ADR-0001 的 summarize 失去截断步骤（换成 coverage 前移 +
  checkpoint 追加）；branch/tail 不变，且「branch」（agent 私有，
  checkpoint 前缀树）与「thread」（公开子 channel）保持区分——
  两者都是带 parent 的日志，差别在可见性。
- agent 循环契约（ADR-0006）重述为：append 自己的记录，读自己的
  投影；scale-to-zero 与无状态照旧成立。
- 新表：messages、checkpoints（按 channel 指针键控）、cursors（多方才有）、
  members（发送者身份）、消息标签索引。全部 OKM 声明；hex stability
  test 锁布局。ns 40 空出（ADR-0010 已用 36/37/38，39 是游标）。
- 策略引擎是 k10r 侧的纯函数（阈值评估、max-gap 分界）；LLM 调用（摘要）
  按 ADR-0007 留在 gravity 侧。
- 指针带 `sub` 之后，切点落在哪一条记录上是确定的：增量读 `(ts, sub)`
  严格晚于覆盖点的行，同一毫秒内的消息不会再被静默吞掉。
- 初始提示词快照让人设更新滞留在「下一次压缩」这个粒度上；换来的是整个
  前缀在两次压缩之间字节不变，缓存可用。
