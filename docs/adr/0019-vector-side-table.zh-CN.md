# 0019 — 向量搬出实体行

> **语言：** [English](0019-vector-side-table.md)（主） · [中文](0019-vector-side-table.zh-CN.md)

**状态：** Accepted 并**已落地**（2026-10-26）——`EntityRow` 上不再有向量，副表是
`NodeVector`（ns 43），两者同一个 batch 提交。
**日期：** 2026-10-26

## 背景

ADR-0018 把 skill 的使用计数作为 prop 放在节点上。prop 住在行的 dynamic segment，而一次
prop 写入就是一次整文档写入（okm ADR-0035）：整行解码、合并、重编码。对一行小字段来说这
没问题——**对这一行不是**，因为同一个 payload 里还装着节点自己的向量。

两个字段的生命周期恰好相反：

| 字段 | 体积 | 变化频率 |
|---|---|---|
| `embedding: Vector<f32>` | 384 维 1.5 KB，512 维 2 KB | 几乎不变——只有 `name`/`title`/`content` 改了才变 |
| `invoke_calls` / `invoke_ok` / `last_invoked` | 每个八字节 | 每次调用都变 |

共用一个 payload 的意思是：写得频繁的那一方，替很少写的大字段付钱。数一次调用，要把一个
计数根本不可能改变的向量重新编码一遍。这不是纸上的成本——每次工具调用都复制一份向量，而且
它随嵌入模型的宽度增长。

## 裁决

**向量搬到自己的表，键类型沿用实体自己的键类型。**

```rust
#[derive(DocumentEncode, Clone, PartialEq, Debug)]
#[ok_ref(EntityKey)]          // 同一个键类型：键 payload 逐字节一致
#[ok_ns(43)]                  // 自己的一个 ns
pub struct NodeVector { pub embedding: Vector<f32> }
```

这是 okm 已有的副表模式（MODELING「字段太大，放进副表」），不是新机制。四条理由，
按它们做决定的顺序排：

**1. 一行，两个毫无共同点的写者。** 向量又大又近乎不变；计数又小又一直在变。任何被两者共用
的 payload，价格都按「碰得更勤的那个写者」结算——也就是计数。

**2. off-row 考虑过，否决了。** 行内注解式的单字段搬离（`#[ok_offrow]`）能装下向量，代价是
一个字段级选择器要穿过 `FieldDesc`、`FieldSchema`、`split_names`、四个整文档动词和 derive
的遍历，而且它**禁止**对该字段做索引。用父键类型的第二张表做同一件事，不需要任何新机械
（okm ADR-0036 的否决，从应用侧再确认一次）。

**3. 主表的写入从此完全不碰向量。** 这一层优势之前没有说出来：拆开之前，**每一次**写这个
节点——包括一次计数——都要重编码向量；拆开之后，热行里没有大字段，所以热写的「小」是结构
决定的，不是靠纪律维持的。

**4. 索引维护不再需要精确。** off-row 形态下，改一个字段就必须先弄清它会喂到哪些索引上、
然后只更新那几个；否则重量级索引——向量是最坏的那个——会被任何一次写带着重写一遍。副表的
索引是**它自己的**：只从那张表重建，所以索引整体更新即可，不需要字段级的记账来保证正确。

## 形状

- **有副行就是有向量。** 不用 `Option<Vector<f32>>`，也不用零长哨兵：没有向量的节点在 ns 43
  里没有行。
- **它不声明任何面。** 向量没有键序；检索仍然是 `okm-vector` 的 `ExactIndex`，只是改为从
  ns 43 重建，而不再从实体行的帧里抠。
- **检索要读两张表**：实体行回答查询落在哪、以及它的过滤条件，然后按 id 取向量。这是拆分
  要付的那笔钱，也是唯一值得盯的地方：落着 `k` 个节点就是 `k` 次点读（或一次批量 multi-get）。
- **删除归调用方**，与这个模型里处处一致：没有级联，所以这对行一起写、一起删。

## 为什么不把它写成 `Ref`

副表的键就是实体的键，两张表之间没有字段级的引用。另一条看起来更顺的路，是让实体行持一个
`Ref<NodeVector, EntityKey>`；四条代价否掉它。

- **读放大回来了。** `Collection::get` 自动解引用，所以每次读实体行都顺带点读一次 ns 43——
  2 KB/次，随模型宽度增长。而拆分的一半收益正是「不需要向量的读不付它」（技能读取、名字点查、
  viz 卡片），带 `Ref` 就永远拿不到。
- **写隔离被 `Ref::own` 破坏。** 父行的 `put` 会把子文档一起写，于是计数的每次 bump 又把向量
  写一遍——正是本文档要拆掉的那件事。改成 `Ref::ref_key` 可以只存 key、不碰子文档，但父行
  仍多一个热段字段，而且键一变就触发释放。
- **没有级联删除，而且方向反了。** `purge` 只删主键条目、面与 reduce 账本，不碰子文档：父行
  删了，副行留下成孤儿——孤儿向量会被 ns 43 的索引重建收进去，落点却是不存在的 id，「有副行
  就是有向量」当场失效。它支持的只是覆盖写时的「换 key 即删除」，方向与「父删子删」相反。
- **那个释放不区分共享。** 推 key 的 derive 对 `own` 与 `ref_key` 一视同仁，所以一个父行重写
  并丢掉某个 key 时，会删掉别的父行仍在引用的子文档（读回来是 `None`）——okm MODELING 说
  「共享的子文档存活」，代码不支持这句话。

判据一句话：`Ref` 表达的是「子文档属于父文档」——身份、生命周期、自动解引用绑在一起；副表
表达的是「同一个身份的两部分，各有各的写者」。向量的键就是实体键，它不需要第二个身份，而它
需要的两件事（写隔离、读按需）恰好被 `Ref` 的两条语义直接破坏。存在性与删除都没有外键担保：
这对行由调用方一起写、一起删。

## 后果

- **一次计数的代价是一行小写入。** ADR-0018 的计数器便宜，靠的是「热行没有大字段」这个构造，
  而不是「段很小」这个假设。
- **重嵌入一遍只写一张表。** 换嵌入模型的宽度只碰 ns 43，不动任何实体行。
- **「派生数据留在图外」变成「留在图旁、在自己的表里」。** 这条拆分还有第二个判据，记在这里：
  **写频率不对称**——一个大字段，与一个频繁的小写者同行，即使每次读都想要它俩，也要拆。它与
  「大 且 被单独访问」并列，不互相替代。
- **拆分之前的 store 是重建，不是迁移。** 行布局升到 v4，`embedding` 从 payload 中间消失了，
  所以 v3 的行在新 schema 下会被解成垃圾；这是刻意的——一个对错位布局耸耸肩的解码器会**静默**
  读出损坏。落地时 `data/` 是空的，所以升级路径就是换一个空目录。若某个 store 真需要带过来，
  界面是 `scan_documents_raw` 加一个 legacy 结构体，解出来分别写进两张表。

## 落地了什么

1. `EntityRow` 去掉 `embedding`（布局 v4）；`NodeVector { embedding }` 在 ns 43 用
   `#[ok_ref(EntityKey)]` 声明，不声明任何面。
2. 新节点的行与向量写进**同一个 batch**（两边都用 `save_with_prev_into`，一次
   `commit_batch`），这对行不可能被崩溃撕开。没有引擎就**完全没有副行**，而不是留一个没人读的
   空帧。
3. `GraphStore::node_vector(scope, node_id)` 返回 `Option<Vector<f32>>`：在场与否就是那个布尔。
4. `load_vector_table` 读 `scope_vectors`（对 ns 43 一次扫描），与它本来就要扫的实体行做连接；
   `ExactIndex` 因此从这张表构建。
5. 有测试：prop 合并之后向量逐字节不变、这对行跨重开存活、检索从 ns 43 重建
   （`mem-core/tests/graph.rs`）。
