# 0019 — 向量搬出实体行

> **语言：** [English](0019-vector-side-table.md)（主） · [中文](0019-vector-side-table.zh-CN.md)

**状态：** Accepted（2026-10-26）。**尚未实现**——行上还挂着 `embedding: Vector<f32>`；
要动的地方列在末尾。
**日期：** 2026-10-26

## 背景

ADR-0018 把 skill 的使用计数作为 prop 放在节点上。prop 住在行的 dynamic segment，而一次
prop 写入就是一次整文档写入（okm ADR-0035）：整行解码、合并、重编码。对一行小字段来说这
没问题——**对这一行不是**，因为同一个 payload 里还装着节点自己的向量。

两个字段的生命周期恰好相反：

| 字段 | 体积 | 变化频率 |
|---|---|---|
| `embedding: Vector<f32>` | 384 维 1.5 KB，512 维 2 KB | 几乎不变——只有 `name`/`title`/`content` 改了才变 |
| `invoke_calls` / `invoke_ok` / `last_invoked` | 每个八字节 | 每次调用都变 |

共用一个 payload 的意思是：写得频繁的那一方，替很少写的大字段付钱。数一次调用，要把一个
计数根本不可能改变的向量重新编码一遍。这不是纸上的成本——每次工具调用都复制一份向量，而且
它随嵌入模型的宽度增长。

## 裁决

**向量搬到自己的表，键类型沿用实体自己的键类型。**

```rust
#[derive(DocumentEncode, Clone, PartialEq, Debug)]
#[ok_ref(EntityKey)]          // 同一个键类型：键 payload 逐字节一致
#[ok_ns(43)]                  // 自己的一个 ns
pub struct NodeVector { pub embedding: Vector<f32> }
```

这是 okm 已有的副表模式（「一个放不进行的值：自己的 ns，同一个键」），不是新机制。四条理由，
按它们做决定的顺序排：

**1. 一行，两个毫无共同点的写者。** 向量又大又近乎不变；计数又小又一直在变。任何被两者共用
的 payload，价格都按「碰得更勤的那个写者」结算——也就是计数。

**2. off-row 考虑过，否决了。** 行内注解式的单字段搬离（`#[ok_offrow]`）能装下向量，代价是
一个字段级选择器要穿过 `FieldDesc`、`FieldSchema`、`split_names`、四个整文档动词和 derive
的遍历，而且它**禁止**对该字段做索引。用父键类型的第二张表做同一件事，不需要任何新机械
（okm ADR-0036 的否决，从应用侧再确认一次）。

**3. 主表的写入从此完全不碰向量。** 这一层优势之前没有说出来：拆开之前，**每一次**写这个
节点——包括一次计数——都要重编码向量；拆开之后，热行里没有大字段，所以热写的「小」是结构
决定的，不是靠纪律维持的。

**4. 索引维护不再需要精确。** off-row 形态下，改一个字段就必须先弄清它会喂到哪些索引上、
然后只更新那几个；否则重量级索引——向量是最坏的那个——会被任何一次写带着重写一遍。副表的
索引是**它自己的**：只从那张表重建，所以索引整体更新即可，不需要字段级的记账来保证正确。

## 形状

- **有副行就是有向量。** 不用 `Option<Vector<f32>>`，也不用零长哨兵：没有向量的节点在 ns 43
  里没有行。
- **它不声明任何面。** 向量没有键序；检索仍然是 `okm-vector` 的 `ExactIndex`，只是改为从
  ns 43 重建，而不再从实体行的帧里抠。
- **检索要读两张表**：实体行回答查询落在哪、以及它的过滤条件，然后按 id 取向量。这是拆分
  要付的那笔钱，也是唯一值得盯的地方：落着 `k` 个节点就是 `k` 次点读（或一次批量 multi-get）。
- **删除归调用方**，与这个模型里处处一致：没有级联，所以这对行一起写、一起删。

## 后果

- **一次计数的代价是一行小写入。** ADR-0018 的计数器便宜，靠的是「热行没有大字段」这个构造，
  而不是「段很小」这个假设。
- **重嵌入一遍只写一张表。** 换嵌入模型的宽度只碰 ns 43，不动任何实体行。
- **「派生数据留在图外」变成「留在图旁、在自己的表里」。** okm 的 MODELING 因此多出一个拆分
  触发器——**写频率不对称**，与原来的「大 且 被单独访问」并列：一个大字段，与一个频繁的小
  写者同行，即使每次读都想要它俩，也要拆。
- **尚未实现。** `/graph/{scope}` 现在从行上读向量；检索路径、嵌入写入、既有 store 的迁移
  都还得跟上。在那之前，这条记录描述的是终态，代码落后一个 ADR——写下来，而不是当没发生。

## 实现要动的地方

1. `EntityRow` 去掉 `embedding`；`NodeVector` 在 ns 43 用 `EntityKey` 声明。
2. 每一次向量写入变成对副表的 put，与实体行同一个 batch 提交（okm ADR-0003：一个 WriteBatch
   = 一个事务）。
3. `retrieve`（以及骑在它上面的 resolver）在落着之后按 id 取向量。
4. `ExactIndex` 改为从 ns 43 构建。
5. 既有 store 的行还带着旧帧里的向量，需要一次性迁移重写；在此之前要么两种形状都能读，要么
   重建 store（现在可接受：语料小且可再生成）。
