# ADR-0006: 无状态 Agent 集成 — 会话即数据

**状态**：Accepted（设计定案，实现未开始）
**日期**：2026-09-08
**英文版**：[0006-stateless-agent-session-as-data.md](0006-stateless-agent-session-as-data.md)

## 背景

传统 agent 架构把会话当作 agent 进程内的**运行时状态**：循环持有消息
列表、原地修改，并负责持久化、checkpoint、上下文拼装。这让循环成为
一切触碰历史的事情的耦合点——记忆注入、压缩触发、框架专属的上下文
管线。

Krystallizer 提供的是相反的原语集（ADR-0001）：对话的容器是只追加的
channel 日志（ADR-0008），完整历史随时可取，agent 的上下文在读取时组装成
投影——checkpoint 记录 + coverage 后的增量 + 未读尾部。既然如此，agent
循环不需要维护任何东西——它可以是一个纯函数：

```
f(projection, user_input) -> records'
```

这与 Aura 的「API 有状态、运维无状态」立场
（aura-architecture.md）同构：会话持久化与恢复沉到存储层
（krystallizer），actor/executor 在调用之间不持有状态，scale-to-zero
顺势免费获得。

## 决策

1. **会话即数据。** Agent 读自己的投影、追加自己的记录；它从不改写历史、
   从不从零拼装上下文、调用之间不持有会话状态。它唯一的写是**追加**
   （含工具结果）。所有函数调用——记忆调用也不例外——都是普通记录：
   循环对调用语义无感，调用只有一种模式。容器是 channel 日志这一点让它
   是结构性的、而非纪律性的：日志本身就禁止改写。

2. **视图层裁剪是另一套机制，不是循环逻辑。** 把函数调用格式从序列化
   视图中裁掉，发生在 krystallizer 的序列化路径上。存储层永远持有
   完整、未裁剪的会话；视图被裁剪，存储不被裁剪。（记忆调用的
   **消解**——把调用记录在视图中替换为召回的上下文——经过评估后
   否决：收益只是省一次往返，代价是循环必须知道哪些调用是记忆调用、
   在轮中重写上下文，一类调用获得循环内的特权待遇，破坏「记录归数据层、循环只追加」的
   不变量。）

3. **循环分解。** Agent 分为四个部分——UI、智能会话上下文
   （krystallizer 的会话+记忆接口面）、执行（工具）、循环。循环收缩为：
   读投影 → 跑 turn → 追加记录。

## 后果

- 循环变得极简且可移植——集成进 Aura 的 actor 模型是直接的：actor
  包住循环，krystallizer 是 sleep/wake 的持久化基底。scale-to-zero 照旧
  成立：进程内不留下任何跨调用的东西，醒来重新读一次投影即可。
- 传输量增大：每轮读一次投影、追加新记录（平均几十条，视图中已裁剪
  函数调用格式）。LLM 请求本来就是全量上下文，这只是序列化成本，不是
  扩展性问题。
- 状态没有消失——是转移了。Krystallizer 承担持久化、并发写、视图时裁剪
  与压缩（作为一条指向日志的 checkpoint 记录，ADR-0008——从不是改写）。
  它是会话真相的唯一持有者；多写者语义是它的问题，但不阻塞本决策。
- 视图层裁剪必须严格只在读侧：任何写路径裁剪会让「存储的会话」与
  「agent 看到的会话」分叉成两个真相。
