# 0016 — 提议是行，晋升是一次声明

> **语言：** [English](0016-skill-proposals.md)（主） · [中文](0016-skill-proposals.zh-CN.md)

**状态：** Accepted（2026-10-26）——同日落地：`mem-core`（`proposals.rs`）、三道门
（`POST /skills/{scope}/propose`、`GET /skills/{scope}/proposals`、
`POST /skills/{scope}/{node_id}/promote`），以及 gravity 那一半（一次 turn 走了两条不同的
code 行时，由它上报这个组合）。
**日期：** 2026-10-26

## 背景

ADR-0015 落地了 skill 回路的读侧：skill 是一个节点，`resolve` 列候选，`invoke_skill` 走一步。
写侧不存在——skill 是人拿 curl 手工声明的，真实的一次 turn 从不会提议任何东西。于是这个回路
在生产里有一个没有东西可解析的解析器。

gravity ADR-0003 §5 早已定下答案的形状：*重复出现的组合是被**提议**晋升的，永不自我挂载*。
缺的是：提议住在哪、谁来写、以及「晋升」到底是一次什么样的动作。

## 裁决

**1. 提议是 kind 为 `skill_proposal` 的实体节点，与事实、skill 在同一个 scope。**

同一张图、同一个存储、同一个 scope——没有第二个集合，没有侧表。把它挡在视线之外的正是这个
kind：`resolve_skills` 只留 `skill` 这个 kind（ADR-0015 §4），所以一个提议在被人晋升之前对
模型是**不可见**的。这也是让「提议而非自我挂载」成真而不是装饰的全部机制：模型选不到草稿，
因为草稿不是候选。

**2. gravity 是唯一的写者，因为 gravity 是唯一的观察者。**

一次 turn 是一次有序的 code 行运行真正发生的地方——每一步都是 gravity 派发的，所以顺序只有
它知道。它在收尾时上报这个组合：`{key, steps, ts_ms}`，其中 `key` 是按执行顺序排列的 code
id（`4+7`），`steps` 与 skill 的 `steps` 是同一份 JSON 文档。

key 由**走路的人**拼，k10r 不推导它，因为 store 不解析 `steps`（ADR-0015 §3：形状归生产方）。
让 store 在这里解析，正好就是那条裁决避开的第二套 schema。

**3. k10r 只计数；没有任何东西自动晋升。**

`POST /skills/{scope}/propose` 以 `key` 幂等：同一个组合再跑一次，是同一行 `count + 1`。
顺序不同就是不同组合（`4+7` ≠ `7+4`），所以 key 是有序的，不是一个集合。

`count` 是 **prop，不是权重**。权重系统的计数器骑在**边**行上（ADR-0005），而提议是节点；
更要紧的是，这里数的回答的是另一个问题——*这次运行重复了吗*——这才是人审时问的。权重面会按
检索排序，那对一份待审队列是错的问题。

一次 turn 走过**两条不同的** code 行才算一个组合；同一行跑两次是重试。这条由 gravity 判断
（运行在它手里），不满足就什么也不上报。

**4. 晋升是一次声明，不是一次改名。**

`POST /skills/{scope}/{node_id}/promote {name, title?, content?}` 读出提议的 steps，用**人**
给的名字、标题与内容声明一个 skill，并在提议上记录 `promoted_to`。

它刻意不是「把这个节点改标签成 skill」：图里没有给实体改标签的写路径（身份就是名字，改标签
就是改名），而且「当初是什么运行提议了它」这份记录会丢。两行——提议带着它的计数与结局，skill
带着它的名字——才是诚实的形状。同一行第二次晋升按名字拒绝，因为一个提议产出两个 skill 是人
为错误，值得报出来，而不是悄悄合并。

**5. 队列是一次扫描，是一道人的门。**

`GET /skills/{scope}/proposals?min_count=N` 扫提议这个 kind，丢掉已晋升的行，按计数排序。
它是扫描而不是一个声明的权重面：队列按构造就小（每个不同组合一行），模型路径上没有任何东西
读它，而「重复次数」的排序是一次 sort，不是一次检索。

## 后果

- **回路的写半边存在了。** 一次做了值得重复之事的 turn 会留下一行；人读队列、给 skill 起名；
  下一个 turn 的 `resolve_skills` 就能提供它。这条路径上没有任何一步需要新的工具名——固定清单
  不变（gravity ADR-0004）。
- **没有任何自动晋升，所以一次糟糕的 turn 污染不了 skill 语料。** 提议由复审封顶，不由小聪明
  封顶。
- **提议带着它点名的那几步的描述**（gravity 走路时把每个 code 行的 `description` 记下来），
  复审的人不必逐个打开 code 行就知道每步做什么。
- **这条路上还留着两项**：（a）面向人的动词——今天队列靠 `curl` 读，晋升要手写一个 POST；
  （b）计数只涨不衰减，所以「一周里噪声性重复」和「一个月里稳定重复」看起来一样。权重系统的
  衰减是边形状的，搬不过来。
- **这里没有任何东西碰检索排序。** 晋升出来的 skill 从落地那一刻起就是一个普通 skill 节点；
  提议它的那个计数留在提议上。
