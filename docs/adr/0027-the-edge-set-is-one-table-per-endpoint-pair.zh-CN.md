# ADR-0027：边集按端点对发布成一张张表

日期：2026-11-11
状态：已裁决并落地 2026-11-11

## 1. 背景

读者想用 SQL/PGQ 对湖问图问题：在已发布的表上声明一张属性图，然后在里面匹配路径。那句声明是读者的 DDL——会话或目录里的对象，用脚本重建——所以图本身没有任何东西要导出。要导出的是声明能点名的表形状。

声明需要两件规范边表给不出的东西。边表的端点列必须**等于**顶点表的键列（`SOURCE KEY (src_scope, src_node_id) REFERENCES entities (scope, node_id)`）；而每条 `EDGE TABLES` 只引用**一张**顶点表。我们的边批带的是 `(src_table, src_pkey)`——一个名字加端点的裸键字节——而且它横跨顶点表，因为一条事实可能指向实体，也可能指向成员。

## 2. 裁决：每个端点对一张表，端点类型化，规范列保留

边集发布成 `facts__<src>__<dst>`——`facts__entities__entities`、`facts__entities__members`、`facts__members__entities`、`facts__members__members`。每张保留规范列不变（`src_table`、`src_pkey`、`dst_table`、`dst_pkey`、`predicate`、边键、负载字段、`variant`），并在 `variant` 之前放上**解码后**的端点键，列名取自该对所指顶点表：

- `entities`——`src_scope u64`、`src_node_id u64`（终点为 `dst_*`）；
- `members`——`src_member_id`，连字符文本，与顶点表的写法逐字相同。

对是**列举**出来的，不是从行里发现的：没有边的对发布成空表。这样已发布的集合是声明的函数，而不是今天这些行的函数，读者的声明也就不会因为出现了第一条第新种类的边而要改。

裸键列保留。还原需要精确字节；留着它们，读者把边连到节点时就不必学键的编解码。

## 3. 代价与所得

湖的表数按顶点表的平方增长（今天两张顶点表：四张边表）。新增一张顶点表就加一行对，每张在装上边之前都是空表。

okm 的边导入改成**按名字**找列并容忍多余列，所以对表仍然是还原喂给图的东西——类型化列不关它的事。这正是这个拆分不需要动还原代码的全部原因：读者据以声明图的那张表，与还原读到的那张表，是同一张。

## 4. 已否决

- **一张宽边表加可空类型化列**（`src_scope`、`src_node_id`、`src_member_id`…… 每行只有一族非空）。SQL/PGQ 的端点列不能为空：空的端点不会报错，它静默地匹配不到任何东西，而一个静默看不见边的图查询比一个拒绝编译的查询更糟。
- **保留一张规范边表、让读者自己建 N 个视图。** 视图和图本身一样是本地 DDL，所以不花字节——但它把一个形状决策推给每个读者，并让「这个湖能不能画图」取决于有没有人写那几个视图。这里是主动换掉的，为的是「发布出来就能画」。
- **去掉裸键列。** 那样还原要么解码出它不敢信的东西，要么每个读者都得学键的编解码（`Uuid7` 的字节序、变宽的字符串键）。多一列冗余比一份共享编解码便宜。
- **从行里发现端点对。** 一对边消失了，旧表会带着陈旧行留在那儿；一对边第一次出现，则与读者的声明赛跑。

## 5. 后果

属性图声明现在可以直接写在已发布的湖上，没有转换步骤；而且随着图增长它一直写得出来，因为空的对表从一开始就发布了。图本身没有任何持久化：声明由读湖的人重新生成，湖只留它本来就要留的表。
