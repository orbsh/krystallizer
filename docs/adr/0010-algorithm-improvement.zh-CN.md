# ADR-0010: 算法改进 —— 写时消解与自动认知分箱

**状态**：已落地（步骤 1–2 于 2026-10-17；步骤 3–4 与读侧于 2026-10-19）
**日期**：2026-10-16
**英文版**：[0010-algorithm-improvement.md](0010-algorithm-improvement.md)

## 背景

主动面（长期记忆，ADR-0001）有表，但没有算法。提取出来的
事实一条条到达（每条一个定长 8 元组），落成散落的节点，没有东西给它们
秩序。秩序只在两个
地方付账：读时（每次检索自己聚类需要的邻域），或写时（在打字间隙跑一遍后
后台，即调用方本就在跑自己活的地方，ADR-0007——事实本身来自模型的主动添加，在轮内）。

本文档取后者：写侧把全部成本——冲突裁决、分箱、子图摘要——收进那趟写时后台内部，
于是读侧完全不跑图算法。文档合并了为这条轨写过的两份草案（散落在
`docs/LPA.md` 的一份：三表 schema、生命周期阶段、可视化延伸；以及一份写时消
解变体：裁决规则、密度边界指标、胶囊 prompt、读侧草图——前三样本文随后退役
（§3–§4）），并纠正了两者共同的
一处：它们把存储写成「字符串前缀 + JSON 值」，这被 okm 的建模规则否掉（键段
里出现变长文本、用手维护的前缀替代访问方法、值用序列化文本）。§1 是同三张
表按 okm 术语的表述。

下面是约束每一步的前提：

- **mem-core 不持 LLM、不持传输、不是 actor**（ADR-0007）。它内部运行的
  一切都是确定性的、本地的；事实来自模型的主动添加（调用方把那次调用接到
  `ingest(fact)`），k10r 从不回调任何人。
- **检索是向量着陆 + 实体名/别名精确点查，然后按权重排序的遍历**
  （ADR-0003）。没有词法分支可复用，也不允许再加第三套
  检索机制。
- **一个 WriteBatch = 一个事务**（ADR-0002）：本算法做的每一处索引变更都
  与数据变更同一次提交。
- **边权来自 ADR-0005 的权重模型**——不引入第二套权重语义。
- **Append-first，不是 append-only**（ADR-0002）：当禁止
  修改比修改本身更贵时，修改是允许的。本文档是这条规则的一个实例，不是从
  「不可变」教条里凿出的例外。

## 决策

### 0. 流水线

```
[ 步骤 1：新事实元组 ] ──► [ 步骤 2：写时消解（upsert） ]
                                    │
                              (写入 Fjall)
                                    ▼
[ 步骤 5：读侧 ] ◄── [ 步骤 4：社区的桶 ] ◄── [ 步骤 3：增量 LPA ]
```

步骤 1–2 在事实经调用方的 `ingest(fact)` 落地时执行；步骤 3–4 在**同一次调用**里、
于该事实自身提交之后执行——没有后台 worker，也没有对存储的第二遍扫描。
步骤 5 是读路径，不跑任何算法。

### 1. 写时规范化与消解（按 okm 术语的布局）

模型的主动添加产出结构化事实（主谓宾三元组，序列化为定长 8 元组），由调用方通过确定性的 `ingest(fact)`
门交给核心；核心不解析散文，也不调模型。这条轨的状态由三张集合承载；符合
okm 规范的布局如下（ns 在落地时分配：实体 36 与事实 37 已落地（2026-10-17），
社区序号 38 于 2026-10-19 落地）。

```text
实体 —— 节点集合（ns 36），每图一个
  0x0 主表           [scope u64][node_id u64]
                     → 行体：kind_id（热）、community_id（热——LPA 的结果，
                       由它自己的面读取）、literal_num（热，i64——字面量
                       节点的整数投影）、name（冷 TLV）、props（动态段）
  0x1 节点种类面     [kind_id u16][scope u64][node_id u64]        声明式索引
  0x1 by_name 面     [name][scope u64][node_id u64]               实体名/别名精确入口
  0x1 by_community   [community_id u64][scope u64][node_id u64]   ← 草案的 index:community:，现为声明面
  0x4/0x5 谓词词汇表  [kind_id u16] → 种类名 ／ [种类名] → kind_id
                     节点种类，与 props 的字段名（0x02/0x03）分开

2026-10-21 更新：节点行的 kind 是 `kind: Vocab<u16>`——一个分类**字段**，标签住在该字段
自己的数据词表里（okm ADR-0032），于是节点侧不再占用 0x04/0x05，也不需要分配代码。
0x04/0x05 这本词表只归**图**（谓词），读方从行上直接取标签（`row.kind.as_str()`），
不再解析 id。wire 宽度没变（两字节），布局版本 3。

事实 —— 边集合（ns 37），每图一个 ns（okm ADR-0017）
  0x0 主表           [edge_id u64]
                     → 行体：[src NodeRef][dst NodeRef][predicate_id][since][confidence][weight]
  0x1 动态段         [edge_id u64] → 关系的开放 props + `functional` 标志
  0x1 声明字段面（每条**声明**的 #[ok_index] 一面，今天两个面各有一个读者：
  by_since 归时间入口、by_scope_weight 归按 scope 的权重排序面——后者把行上那份冗余的
  `scope` 放在前面，PLAN 4a）
                     [字段值][edge_id u64]
  0x4/0x5 谓词词汇表   [谓词名] → predicate_id ／ [predicate_id] → 谓词名
  0x6 谓词索引       [predicate_id][edge_id u64]
  0x7 出边           [src NodeRef][edge_id u64]
  0x8 入边           [dst NodeRef][edge_id u64]
  0x9 谓词+出        [predicate_id][src NodeRef][edge_id u64]
  0xA 谓词+入        [predicate_id][dst NodeRef][edge_id u64]

  这一侧没有 SCOPE 段：边集合是 `Graph<S, E>`，自己造键（okm 的边形态），
  所以归属边界走**端点**——每个 `NodeRef` 携带它自己的实体键，scope 在其中。
  一次遍历从带 scope 的节点出发，也就一直在 scope 内；只有整 ns 的扫描
  （0x6，「某个谓词的全部边」）会跨 scope，那是调用方按端点过滤的事。要在边键上
  带 per-scope 前缀，就得绕开 okm 的 Graph 手写这个集合。

社区序号（ns 38，2026-10-19 起每 scope 一行）
  0x0 主表           [scope u64]
                     → 行体：high_water（热：最后发出的社区 id；
                       单调递增，所以 id 永不复用）
```

`scope` 领在每个主键前段，因为语料按 user 分（ADR-0003）——那是有属边界，
与 flat memory（`[user_id][id]`，ns 32）同形，不是优化。`NodeRef` 是
`[ns 2B][len varint][pkey]`，自描述（okm ADR-0017 §2），因此任何节点集合都
零声明参与。

一个词项的属性——元组的 head/tail props——落在实体行的动态段上：那是这个
实体的属性，被关于它的每一条事实共享。它们是**合并**的，且合并是已裁决的
读法：同名属性取较新的值，其余存活。整段覆盖会让一条事实的属性抹掉同一
实体上其它事实的属性，这是它被否掉的原因。

与草案不同的五处，以及原因：

- **名字永不进键，也不往键里塞哈希。** `KeyEncode` 在编译期拒绝 `String`；
  把哈希塞进定宽段会静默撞车（撞到就是寻址到另一个实体的行）且渲染不回来
  ——这正是 okm 用代理 id 的理由（MODELING「Open vocabularies」）。实体名住
  在 `by_name` 面和行的冷段里，路径是 `name → node_id`。草案的
  `community_id = hash(entity_name)` 种子与 `c_milkyway_2026` 式 id 一并去掉：
  一个社区以「成员节点上的那个值」存在，其 id 由本 scope 的序号行发出（单调递增，
  永不复用），它的人类可读面孔是渲染文本的表头（`community c7`）。
- **每个查询维度都是声明式访问方法，而不是埋在键里的前缀。** 社区反向索引
  就是 `by_community` 面（`[community_id][scope][node_id]`），它的尾部就是主
  键编码——可解码，符合 okm「索引条目的尾部可解码、主键的自定义尾部不可解
  码」这条规则。手写前缀方案正是这条规则要防的东西。
- **这里任何地方都不用 `[order]` 段。** 主表读都是点读与遍历读，不是复数有
  序范围读，而排序键只有在结果是复数时才配得上它占的字节（okm MODELING
  「Key naming」）。`since` / `updated_at` 是 payload 字段，遵 ADR-0005 自己
  的先例：可变元数据永不进键。
- **种类是运行时数据，算法要查的三个边字段是声明字段。** 谓词通过**图自己的
  谓词词汇表**分配（固定面 0x04/0x05，name → `predicate_id`，okm ADR-0017 §3）
  ——它不再等于载荷的字段词汇表（0x02/0x03）；节点种类在实体集合里走同一条规则
  （自己那一对 0x04/0x05，props 名留在 0x02/0x03）；而 `since` / `confidence` /
  `weight` 是 k10r 自己 schema 的声明字段，各得一个 0x1 面（okm ADR-0017
  §3）——在 okm 的设计里这两者正交。提取出来的、开放式的属性走动态段，需要
  查询时通过 path 索引（okm ADR-0012 / ADR-0029）到达。
- **事实元组里的关系是「名字 + 属性」，没有自己的标签。** 那个名字就是这个
  `predicate_id`：再加一层更粗的种类，既没有面、也没有读者（模型想让某个分类可见，
  就放进属性，查询时经 path 索引到达）。所以元组的三个角色并不对称——head /
  tail 带名字**和**种类（实体行的 `kind_id` 加 `node-kind` 面），关系只带名字。
- **值用原生段，不用 JSON 大块**（okm ADR-0018）：定宽字段连续（热），变长
  文本作冷 TLV 段。

新落地的事实是一个散落节点，带一个独立种子标签——种子是一个新社区 id，不是
哈希。

**消解：在事实写入前先找在场者。**

```
                        新事实传入
                             │
                             ▼
   扫一次 0x9 面：这个源出去的、这个谓词的边有哪几条？
                             │
          ┌──────────────────┴──────────────────┐
          ▼ (没有)                              ▼ (有在场行体)
      新 link 一条边                  执行裁决：
      （平行边是各自独立的事实）      new.since > old.since
                                     OR new.confidence >= old.confidence ?
                                            │
                          ┌─────────────────┴─────────────────┐
                          ▼ (是)                              ▼ (否)
                    原地改写行体                        丢弃新事实
                    （同一个 edge_id）                  （或降低其权重）
```

草案的两处记账在 okm 的机制下消失：

- **不用手删索引条目，也不用墓碑。** 草案得在同一个 batch 里手动删掉旧索引
  条目；okm 的声明式面是从行派生出来的，改写行就重生成它的面条目（weight /
  since / confidence），陈面不可能残留。
- **平行边是各自独立的事实**（okm ADR-0017）：同一个 (src, kind) 配不同客体
  是另一条边、另有 `edge_id`，所以覆写只适用于「在一个源上函数式」的关系种
  类——种类如何声明其基数见「欠账/未决」。

```rust
// 草案草图 —— mem-core，在一条新提取的三元组上（按 okm 形态）
let predicate_id = kinds.id_of(predicate);   // 图谓词词汇表（0x04/0x05）：name → predicate_id
let src = NodeRef::new(&ENTITY_NS.to_be_bytes(), &subject_id.to_be_bytes());
let dst = NodeRef::new(&ENTITY_NS.to_be_bytes(), &object_id.to_be_bytes());

// 1. 这个源出去的、这个谓词的边：扫一次 0x9 面
let incumbent = edges.typed_out(predicate, &src).next();

let mut batch = edges.batch();
match incumbent {
    // 2. 与在场行体做裁决
    Some(edge_id) => {
        let old = edges.get(edge_id);
        if new_fact.since > old.since || new_fact.confidence >= old.confidence {
            // 原地：同一个 edge_id，行的面随行而来
            batch.put(edge_id, new_fact.into_body(src, dst, kind));
        }
        // 否则：丢弃，不写
    }
    // 3. 无在场者：link 一条新边（0x6/0x7/0x8/0x9/0xA 同批，谓词首见时另加 0x4/0x5）
    None => batch.link(EdgeFact { src, dst, kind, ..new_fact }),
}
batch.commit();   // 一个 WriteBatch = 一个事务（ADR-0002）
```

### 2. 增量标签传播（LPA）

Append-first 的写入产出的是堆，不是秩序；秩序按每次写入在内存里局部划定，
而不是靠一遍全局。

**为什么用局部增量 LPA。** 它的成本在受影响的邻域上接近 O(E)，不需要把全
量大图装进内存，而且它正是 ADR-0003 里说的那种值得引依赖的算法（社区发现
在那里被点名为「简单算法直接实现」的例外）。内存图的载体是 `petgraph`。

机制：

1. **构建局部子图**——通过遍历面（0x7/0x8、0x9/0xA）载入新写入的节点及其
   直接相连的 2-hop 邻居，在内存里组装成一张临时图。不载入全量图。
2. **邻居投票**——节点审视邻居的 `community_id`，以边 `confidence` 乘累积
   边权投票：
   `Target_Community = arg max over C of Σ_{e ∈ Edges(C)} Weight(e) × Confidence(e)`
3. **收敛与提交**——常见情形 3 轮足够收敛（草案允许 3~5 轮）。胜出的
   `community_id` 写进成员节点行的字段。`by_community` 面确实由行**派生**，
   但 okm 的文档覆盖会把旧的索引条目留在原地（条目 key 编码了被索引的值，新值
   落在新 key 上）——所以重新分箱必须在**同一个 batch** 里删掉旧的面条目。
   本文早先"不需要墓碑"的说法是错的，落地时被代码抓住。不再写别的东西——没有
   摘要状态可标。全部走同一个 WriteBatch（ADR-0002），序号行也在其中。

这一遍跑在 `ingest` 里，在事实自身提交之后，所以落地的事实会在调用返回前就分好箱。
首次落地的节点从本 scope 的**序号行**取号（每 scope 一行，单调递增）：水位只涨不
回落，所以即便一个社区整体离开，id 也永不复用。投票不会退化成全零平票
——一条新断言的权重已经是 `ln(2) × 0.5`——平票取**更小**的 community id，所以
结果不依赖迭代顺序。移动过的每个节点与序号行在同一个 batch 里重写。

### 3. 社区在**读时**封顶，不在写时

写侧不再给社区做任何摘要。密度水位线与未压缩事实数水位线一并退役：它们存在的
意义是决定「这个社区什么时候值得一次 LLM 摘要」，而现在没有摘要了。

需要封顶的是**答案**。社区靠累积长大——LPA 随着事实连线不断并点——所以它的规模
在构造上没有上界。于是读侧给答案一个事实预算（默认 20 条，门上 `?budget=`，
0 = 不封顶），按 ADR-0005 的序从**权重最低**的开始丢，并在表头写明省略
（`showing 8 of 15`）。绝不截半行：一个指向「半条事实」的 id 比没有 id 更糟。

如果哪天省略成了某个语料的主调——表头每次读都会说——修法是写侧加一条拆分规则，
那是一个等这个数字出现的后续件，不是现在拍一个阈值。

### 4. 没有固化这一遍：读时直接渲染社区

早先的设计在社区上放一份 LLM 摘要（「胶囊」），由调用方拉取、用 `PUT` 回写。
它退役了，两个理由：

- **那是一件杂务，不是一个面。** 消费方得列待固化、拉包、跑模型、再写回来——
  在一扇只为「取记忆」而存在的接口背后挂着第二份工作量。消费方本来就在跑
  LLM；让它顺便维护 k10r 的索引是笔错的交换，也正是「内部索引不许变成消费方
  的活儿」这条裁决否掉的形态。
- **信息本来就在。** 一个社区的理解**就是**它的节点与边。摘要是对这件事的有损
  投影，而且下一条事实落进来它就过期。

所以没有胶囊表、没有 `pending` 状态、没有包、没有回写、也没有摘要 prompt。
社区在被读的时候渲染（§5）。

### 5. 读侧：先着陆，再取着陆到的社区

读路径不跑图算法，也不调模型：

1. **着陆**——查询嵌入后种子返回（ADR-0003），每个种子带着它节点的 `community_id`。
2. **取着陆到的社区**——种子的社区，按种子序去重（第一个着陆的社区就是查询最
   关心的那个）。
3. **读桶**——社区的成员走 `by_community` 面，事实走遍历面配成员判定（两端都在
   社区内），每条边只出现一次。
4. **渲染**——每个社区一块：表头（规模，以及预算裁过时的省略数），每个节点一行
   （`n12 简洁 [style]`），每条事实一行
   （`e34 n12 -[PREFERS]-> n15 · w=1.400 · c=0.90 · since=…`）。每一行都带它
   所指的 id，因为那个 id 就是调用方要去指的东西——今天指它多读一行，将来指它
   精确修改那一行。

**渲染归 k10r，不归调用方**——记忆的消费方不需要知道图是怎么装配的，第三方 agent
更不知道社区切片是什么。所以答案只带**一种**表示，由 `format` 选择：

- `plaintext`（默认）——上面那个行式形态，进 prompt 用的；
- `markdown`——同样的行，换成标题与列表；
- `mermaid`——`graph LR`，一个社区一个 `subgraph`，关系名做边标签（图上的标签
  只带关系：计数器是**读**出来的，不是看出来的）；
- `struct`——只给数据（种子、社区 id、事实），**完全不出文本**；要自己装配图的
  调用方点这个。

三种文本形态陈述的是同一批事实，差别只在语法。`format` 值不认识就是 400，绝不
静默退回另一种表示——拼错不该悄悄改变答案的形态。

答案是**一扇门**：`GET /memories/{scope}/recall?q=&k=&budget=&ts_ms=&format=`，一次
返回种子、社区 id、被展示的事实和渲染好的文本。没有 N 跳：社区**就是**那块有界
的切片，想要更深的走法，调用方从 `out_edges`/`in_edges` 自己组合。

文本是确定的：同一份语料、同一个预算、同一个格式，答案一模一样；时间衰减只按
ADR-0005 说的那样改变顺序。

### 6. 前端延伸（不新增机制）

持久化的 `community_id` 可以零成本交给可视化：确定性的元组 → 渲染格式转换（不
经过 LLM）喂给 **3d-force-graph**——WebGL/three.js 的力导向图库，带轨道式相
机控制，即本仓 `docs/kg-demo-3d.html` 已经在用的那条载体。那个 demo 把节点/
边的数据包流式推入运行中的布局，并按批重新加热模拟，而不是重画整棵树，正好
就是这里的生产者形态。节点颜色绑定 `community_id`（一个社区一个颜色簇）、
节点大小绑定权重，于是长期记忆里秩序的生长——分箱本身——直接从
`GET /graph/{scope}` 就能看出来：它现在给每个节点带 `community_id`；演示页仍按
节点 kind 上色。

## 后果

- **本文档是 append-first（而非 append-only）的活例。** 边行体、节点行与序号行
  原地覆写，因为把已被取代的版本留成第二行更贵：它会同时毒害检索和读它的分箱。
  日志形状的表（ns 33/34）不受本文档消解步骤的影响。
- **本设计里每一次读都是声明式访问方法**（okm：「访问方法是强制的」）：桶是
  `by_community` 面，消解查找是 0x9 面，精确入口是 `by_name`。不引入裸前缀
  扫描，也不引入通用全表扫描面。
- **键里不带文本、不带哈希值。** 实体名与社区标签住在 payload 字段与索引段
  里，因此能渲染回来、能按人类可读的方式枚举；身份是由水位发放的代理键，永
  不是塞进键段的哈希。
- **不新增检索机制。** 社区是事实图上的一个投影，答案是它的渲染，
  从不是计分分支；检索仍由着陆或实体名/别名精确点查进入（ADR-0003）。
- **投票消费 ADR-0005 的权重**（`Weight(e)`、`confidence`、读写四象限）。
  ADR-0005 不声明权重面：按 `[weight][edge_id]` 的条目会服务整个库（边键不带
  scope，端点才带），所以 scope 级 Top-K 在那里是一张投影表，不是一个面。
- **这里的每个数字都是策略参数**，属于 `config/krystallizer.kdl`（ADR-0008
  的规则）：密度阈值、未压缩事实水位线、迭代上限、2-hop 半径。今天它们是
  `graph.rs` 里的命名常量；提升为 config 是加一个 config 节点，不是改 schema。
  消息计数水位线
  （草案里的 100 条消息）不是 k10r 的——何时添加归推理的那一方（ADR-0007）；
  k10r 只接手递给它的事实。
- **重划分在结构上就是便宜的。** 一个节点换社区只改写一行，并在**同一个 batch**
  里换掉那一条面条目（okm 的覆写会把旧条目留在原地）；反复分箱永远不会变成
  跨越一次扫描的读改写，也不会等文件锁。

### 欠账/未决（本文档未定案的部分）

- **表：** 实体集合（ns 36）与事实边集合（ns 37）已于 2026-10-17 落地；
  ns 38 自 2026-10-19 起装社区**序号**行（每 scope 一行，发号用）——曾经装胶囊
  的那张表已退役（§4）。
- **函数式 vs 多值种类——2026-10-17 关闭。** 由调用方**按每条断言**声明，
  放在关系的 props 里：`{"functional": true}` 表示「在一个源上一个值」，于是
  到达的事实会与同源同种类的在册边裁决；缺省（或 false）表示多值，事实挂一
  条平行边。这个缺省是安全侧——丢一条事实不可逆，多一条边可恢复——而声明随
  断言走，因为发出三元组的模型才是知道该谓词基数的一侧。存储不裁判：同一谓词
  在不同断言里声明不一致，是数据层的事，由每条到达的事实自行决定。该声明留在
  边的动态段上（断言自己的记录）。
- **社区的承载位置——已定，2026-10-19 落地：在节点上。** 两份草案互相矛盾——
  `community_id` 在事实行上（它们的消解/索引代码）还是在实体节点上（它们的
  LPA 与密度指标）。LPA 在节点之间投票、`|V|` 数的也是节点，所以节点行带它，
  配一条 `by_community` 面；社区的边通过遍历面配成员判定取回。只有当读侧必须在
  没有端点行的情况下直接给边时，边侧才需要再开一个面。
- **字面量客体——2026-10-17 关闭。** 字面量成为**节点**：种类 `literal`，
  精确文本进 `name`（`by_name` 入口），整数投影进声明的热字段 `literal_num`。
  理由是形态一致——每条事实恒为两个节点加一条边，于是遍历、分箱与密度指标都
  不需要特例——而值的数值形态是声明字段，区间/最近读就仍然是有序键扫描，不是
  向量距离的猜测。其中仍欠：日期与非数字字符串的规范化投影（今天只有整数会
  投影）。
- **胶囊调用的载体——2026-10-20 退役。** 没有固化调用，也没有承载它的门：读时
  直接渲染社区（§4–§5）。四扇拉取门（待固化列表、桶读、包、`PUT`）随胶囊表一起
  删除。
- **社区 id 的发放——一条序号行（2026-10-20）。** 每 scope 一行
  （`CommunitySeqKey { scope }` → `high_water`），与携带该 id 的行写进同一个
  batch，单行路径上也单独落盘。它只涨不落，所以即便一个社区最后一个成员离开，
  id 也永不复用——这正是「读现存社区的最大值」会弄错的情形（上一版发号器，
  在此退役）。
- **一个 ns 两套词汇，对上 okm 按 handle 缓存的词汇表**（2026-10-17 踩出来的，
  当天因 okm 的裁决而**退役**）：边 ns 里曾同时住着关系种类（okm 的 `Graph`
  用长驻 `VocabCache` 分配）与关系 props 的名字（k10r 分配）；两个 cache 在同一
  本词汇表里分配会把同一个 id 发给两个不同的名字——帧随后以**错误的名字**读回来，
  而且无声。okm ADR-0017 §3 把谓词词汇表与载荷字段词汇表分开（谓词 0x04/0x05、
  字段名 0x02/0x03）之后，这个撞名结构性消失，k10r 的两条纪律——「分配一律走
  一次性 cache」「边 handle 每次调用现建」——随之退役。**读侧也已付清
  （2026-10-19 落地）：** okm 的 `VocabCache::id_get` 在探测时自加载词汇，新建
  handle 直接答类型化读，不必预热——`facts_primed` 那段壳已删除。**实体侧同样
  对称**（kinds 走 0x04/0x05，props 名走 0x02/0x03），那边的"一次性 cache"
  纪律一并退役。
- **函数式改写是一个引擎提交——已付清（2026-10-19）。** okm 的
  `Graph::unlink_into` 把删除集放进调用方自己的批，于是一次改写就是
  `unlink_into` + `link_into` 的一个提交——正是 ADR-0002 要的。边的动态段是
  k10r 自己的条目（不属于 okm），所以同一批里先删它：改写永远不会继承上一条断言
  的 props。这个窗口是关掉了，不是靠重放 ingest 缓过来的。
- **边的载荷编解码归声明所有——已付清（2026-10-19）。** 边的载荷就是一份 obj
  （okm ADR-0017 §3），声明是 `GraphEncode`，于是一份声明同时生成双向编解码与
  面条目：`FactEdge::encode_payload` / `decode_payload`，`since` /
  `confidence` / `weight` 各一条显式 `#[ok_index]` 面。k10r 手写的 `from_attrs`
  （自带 13 字节宽度）与那把锁测试一并删除；裁决输入改成
  `FactEdge::decode_payload(&body.payload)`。
- **k10r 的前缀扫描还按作废的 4 字节头写的——已修（2026-10-19）。** okm
  ADR-0030 之后固定面是一字节，主表键头是 `[ns 2B][0x00]`（3 字节，不是 4）。
  四处读路径仍在按旧形状拼前缀或在 offset 4 处解码：channel 日志
  （`messages_after`——每次读回全空）、按用户的记忆读（`search` / `list`）、
  实体 scope 扫描、以及重开库时的 edge_id 回收（会发出重复 `edge_id`）。
  现在一律走 `write_slot` + 3 字节偏移。
- **草案的前缀布局是作废，不是保留**：手维护的 `node:` / `index:community:`
  前缀在上文被 okm 的面取代，于是草案「一个字段两种键形状」的矛盾被关掉，而
  不是被继承。
- **描述「今日布局」的旧拼法已就地扫掉**：ADR-0002 自己那行与 MODELING 的
  访问方法清单已改写（2026-10-17）。ADR-0005 的计数草图同样已重述：计数住在
  边行上（2026-10-19），旧的 `edge:{src}:{label}:{dst}/read/{ts}` delta 键只作为
  多写者退路的「未定 key 布局」存在。
- **与 PLAN 的关系——已定。** 社区发现原本位于 Phase 5+（「dreaming
  consolidation——petgraph 社区发现 + 人工审核的操作集，不要提前开工」）。
  本文档的增量局部形态已随 Phase 3 的写侧落地（2026-10-19）；Phase 5 留下的是
  全局、人工审核的那一遍，那是另一件事。
- **照草案搬过来、本文档未实测的说法：** 毫秒级读延迟、provider 侧
  context cache ≥90% 命中率、「Rust 内核代码量缩减一半」。它们是这个形态的
  理由与目标，不是结果。

## 历史

**草案原本是什么，为什么被换掉。**

- **分箱的位置。** 流水线把步骤 3–4 放在写入之后的一次后台里，那需要 worker、滞后
  和一套派生失败的重试故事。它们改为跑在同一次 `ingest` 调用里、在该事实自身提交
  之后：一遍局部计算，坏派生就是调用方的一次重试。
- **社区 id 的发放者，改过两次。** 本文最初点名 okm 的 `HighWater` reduce；第一次
  落地换成从胶囊表读「本 scope 当前最大值加一」——少一个机制，但保证也跟着丢了：
  社区离开会拉低那个最大值，id 可能被发第二次。序号行（§1）用一行把保证补回来。
- **胶囊，以及承载它的那些门。** 设计里每个社区一份 LLM 摘要，由调用方拉取（四扇
  门：待固化列表、桶读、包、`PUT`）——2026-10-19 落地，2026-10-20 退役。它让消费方
  去维护 k10r 的索引，又把「节点与边本来就是的东西」重新推导一遍。读侧现在直接渲染
  社区（§4–§5）。
- **「重新分箱不需要墓碑」。** 在 okm 的覆写语义下是错的，已在 §2 更正：旧的面条目
  会在重写后存活，所以重新分箱必须在同一个 batch 里显式删掉它。
