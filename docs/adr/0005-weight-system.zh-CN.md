# ADR-0005: 权重系统 — 计数在边行上、读写比四象限、工具索引

**状态**：已落地 2026-10-19（计数住在边这一行上；delta 追加表只作为多写者的退路保留）；2026-10-22 追加近期访问环（payload 布局 v3）；2026-10-23 加宽为两个环、payload 布局 v4，时间移到查询期——已接受，尚未落地
**日期**：2026-09-08
**英文版**：[0005-weight-system.md](0005-weight-system.md)

## 背景

graph-memory 设计为每条 fact 边配一层系统权重元数据（区别于业务
属性）：read_count、write_count、tool_invoke_count，以及给它们记时的
访问环。读写比划分四象限（核心区 / 深水区 / 噪声 / 冷区），检索
顺序按权重 Top-K（渐进式加载）。

两个工程问题：如何计数才没有 read-modify-write 争用；如何服务按权重排的 Top-K
才不全表扫描。

## 决策

**计数：边这一行就是计数键。** `read_count` / `write_count` / `tool_count` 是
`Facts` 的声明热字段（ns 37，payload 布局 v4），fold 出来的 `weight` 就住在
它们旁边。一个身份、一次写——而 okm 的声明面是从行派生
的，所以加一次计数只重写一行，派生的一切随之跟上。

**近期访问：行尾两个定长环（布局 v4）。** 计数回答「多少次」，却答不了「这个
分布长什么样」——50 次挤在一周里和摊在两年里，查询期衰减算出的账完全不同。
`recent_read: Vector<u32>` 与 `recent_write: Vector<u32>` 落在载荷尾段，读、写各
一环：每环 8 槽、从 `1_767_225_600`（2026-01-01T00:00:00Z）起的**秒**偏移、升序、
`0` = 未用、写入时右移一格。做成两个环而不是一个，是因为写环回答「这条事实最近
一次被重申是什么时候」，一个「最近一次访问」的时间戳分不开它和「最近一次被读」。
`#[ok_len(8)]` 把「永远 8 槽」钉在两环的写边界上（`Default` 是手写的，补齐 8 槽；
旧版本行缺这一帧时按声明的默认补 8 个 0，所以加这个字段不需要清库重建）；代价是
每行多 32 字节。
此后这一行上带时间的字段只有这两个环——旁边不再有 `last_read` / `last_write`
——重排的衰减基准取各环里最新的非零槽。取舍的判据（为什么不是 `Offset`、
`Bytes`、游标，为什么不做成 okm 的 wrapper）记在 okm
MODELING 的 k10r 案例里。

- **谁加谁。** `write_count` 是事实自己的断言：`ingest` 在 link 或赢得裁决时加一
  （被丢弃的事实不算写）。`read_count` 是送出的 recall——只有调用方带着时钟
  （`ts_ms`）时 `recall` / `expand` 才加，因为没人盖戳的读不算读，缺失的时间戳不能
  凭空造出一个访问时刻。`tool_count` 是调用方上报的工具调用
  （`POST /memories/{scope}/edges/{id}/touch`）：k10r 看不见内部的工具调用，用过这条
  事实的消费者自己报。
- **read_count 与 write_count 物理上保持分开**——原子事实追加模型保证读写独立，
  这正是二维四象限分类在存储层稳定的前提。
- **fold 点在访问处，不在后台。** 一次 touch 用一个 batch 重写这一行：计数加一、
  对应的环右移一格，同一行、同一次写。delta 追加表仍是多写者的**退路**：它折进
  同样的字段，切过去不改 schema，落地时唯一要钉的是它的 key 布局。

**权重公式**（沿用 wiki，含工具索引）：

```
weight = read_score + write_score + tool_score

tool_score  = log(1 + tool_invoke_count) × 1.5
read_score  = log(1 + read_count)
write_score = log(1 + write_count) × 0.5
```

深水区（高读低写）是承重墙：硬性的写阈值会结构性打击高录入成本的专家知识。
读 1.0 对写 0.5 就是那个纠正本身——再立一对阈值只是把系数差重说一遍。

- **`weight` 是排序键，不是派生缓存。** 公式是它的默认生产者；外部写入者可以直接
  给绝对值（0 = 未设，即走公式）。不新增第二个字段。主观值在这一阶段**不进**公式
  ——这一阶段要的是「以后调公式要用的数据先在」，不是「公式已定」。
- **桶。** 存的是公式的毫单位（× 1000，四舍五入，下界 0）：小浮点要有一个稳定的
  有序整数才能按整数比较，而 0.001 比三个对数项能取到的最小步长更细，所以分桶
  不会把公式本来分得开的两条事实排成同序。系数是 `mem-core/src/graph.rs` 里的
  命名常量（读 1.0、写 0.5、工具 1.5）。它们是公式本身，不是部署旋钮；要做策略层
  就开一个 config 节点，而现在没有读者。
- **排序。** `recall` 的种子保持相似度序，事实按权重降序（稳定排序，等权时保留
  把它拉进来的种子序）；取回的这一批随后在查询期用两个环按近期活跃重排。着陆仍归
  ADR-0003，权重归本 ADR。

**这一行为以后调公式带哪些字段。** 字段在公式定下来之前就先加宽，是有意的：三个
计数、两个访问环、`confidence`（已声明；今天只有 LPA 投票读它），以及排序键本身。
以后某一项需要、而今天没有的——事实引用事实的计数、按 id 取用的独立计数——等消费
它的那个读出现时再加：没有扫描者的字段，就是一次没人要的写。

**Top-K：scope 级的面已声明，裸的权重面不声明。** 裸面 `W:{weight}:{edge_id}` 答的
是「全库最重的边」，不是「这个用户最重的事实」：边的身份上没有 `scope` 段
（ADR-0010 §1，归属走端点）。scope 级由另一个面承载：边行带一份**冗余的** `scope`
（源端点 scope 的副本，写一次），于是 `by_scope_weight { fields(scope, weight) }`
以 `[scope][weight][edge_id]` 为键、可以按 scope 探针，`top_by_weight(scope, k)`
探它、只解码 k 行——O(k 行) + O(scope 键)，行边上不需要再维护一张投影表。权重变更
也不会让它悬空：okm 裸集合的覆写确实不删按**旧值**建的那条条目，但改写会在边自己的 id
上重新声明它，而 k10r 在动态段那一个批里顺手退役旧载荷写下的条目，所以测试锁住「一条
事实只占一个排序条目」。recall 的排序不需要它：要排的集合已经在手上，近期活跃的
重排也在那里发生。`by_confidence` 与裸的权重面同样不声明：两者都没有读者。

## 后果

- 今天的排序是对 recall 已经取回的那个集合做内存排序——没有索引、没有全表作业、
  没有第二个引擎；近期活跃的重排走的就是这一次排序。
- 冷层作业（Phase 5+ 的淘汰）与渐进式加载（Phase 4）要的是同一个 scope 级面
  （`by_scope_weight`）；哪一个先到，同一个面同时服务两者，而它的形态上面那条决策
  已经写明。
- 存储值里没有时间项，所以它在两次写入之间不会变旧，任何派生状态也不会陈旧。
  近期活跃度是查询期对 recall 已取回集合的重排；按近期活跃排序的 scope 级 Top-K
  因此没有面——它天生会陈旧。要加，等一个接受这一点的读者。

## 历史

**2026-09-08 的草案，在计数这半落地时（2026-10-19）退役。** 它按追加 delta 计数
——`put edge:{src}:{label}:{dst}/read/{ts} → +1`，后台 fold 进
`put edge:{src}:{label}:{dst}/count/read → N`——并从一张声明的权重二级索引
`W:{weight}:{edge_id}` 服务 Top-K，每次权重变化写新键、删旧键（tombstone）。

- 那些 delta 键错了两次：一是写在一个作废的**层**上（`edge:{src}:{label}:{dst}` 不是
  k10r 的键形态——边的身份是 `[edge_id]`，端点与词汇表分配的 `predicate_id` 以 ref
  承载）；二是 delta 表本身对单写者毫无收益，而存储今天就是单写者。
- 计数键也不需要旁表：计数器就是它所计的那一行的字段，所以一次 fold 是一次行重写。
- 声明的权重面死因与上面 Top-K 那条相同：它服务整个库而不是一个 scope，而且它会
  为一个不存在的读者被维护。tombstone 规则随之一起走——没有面留下，也就没有东西会
  悬空。
