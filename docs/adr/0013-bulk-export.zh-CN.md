# ADR-0013：备份就是同一扇门上的 Parquet 导出

日期：2026-10-20
状态：已裁决并落地 2026-10-20——文档表已导。**2026-10-21 更新**：门改成按**表名**寻址而不是
ns，name↔ns 由一份 catalog 文件承载，事实表按 okm 的边表导出，reduce 作为派生表单独走（§2、
§4、§5）。§3 的理由不变；旧的 §4 理由错了，在那里改正。

## 1. 背景

ADR-0007 定的是：批量读仍然是同一 HTTP 边界上的读——没有管理 CLI、没有第二套存储、不
在数据旁边自创一种转储格式。备份正好就是这样一次读（「这张表的全部」），它留下的问题是
**格式**，不是传输。

两种答法。自创一种（k10r 写 JSON 或 CSV dump），或者用 okm 已经有的桥：okm ADR-0007 的
eager Arrow 导出按行**声明**把一个 collection 变成 `RecordBatch`，`parquet_io` 再写成文件。
只有第二种不会漂：列由「生成键编码与载荷帧的那同一份声明」生成，所以改结构是一处改、
改名不可能只改一边。

## 2. 决策

**`GET /export/{table}`——一张表、一个文件、`application/vnd.apache.parquet`。**
**`GET /export`——catalog：`(table, ns)`，一张表一行。**

- **地址是表名，不是 ns。** ns 是存储自己的寻址（ADR-0010 §1 的 ns 词汇）：它在**库内**标识
  一张表，对打开文件的人没有意义。备份是在库外被读的，所以它在库外被命名。名字声明在 ns
  声明的地方——okm `#[ok_name]` → `Document::TABLE_NAME`，与 `#[ok_ns]` 同处——所以两者不会
  漂，并且改名不动任何已存字节。
- catalog 是 name↔ns 方向的那份文件。纯分析用不到它（导出的列已经自带标签）；导入要用，任何
  「ns 41 叫什么」的问题也要用。它在导出时由同一批声明生成，所以不是第二张要同步维护的表。
- `Content-Disposition` 把文件名定为 `<table>.parquet`，于是一目录的导出不用打开就能看出
  各自是什么。
- schema 是 okm 的，不是 k10r 的：带类型的列、`Vocab` 字段导出成它的**标签文本**（没有名字的
  id 导出为 NULL）、定宽声明字段按宽度、`Vector` 字段按元素展开。k10r 只决定导出哪张表、
  文件落在哪，别的不碰。
- okm 的 `export_parquet` 写的是**路径**，所以这扇门写进临时目录再把字节回给调用方。答案是
  请求时刻的**快照**：响应构造完成之后才写进来的行不在这个文件里。
- 本服务没有的表名是 404，并指向 catalog。空表是 200 加一个合法的空 Parquet 文件——「这张表
  是空的」本身是备份该带的信息。
- 行的**开区间**以 `variant` 列随行：声明字段仍是带类型的列，动态段（边的 props、实体的属性）
  是旁边的一列。没有它，文件只带每行的类型化半个、把其余悄悄丢掉——这扇门的第一版就是这样。

**粒度：一表一文件。** 另一种答法是「一次备份一个归档包」，它换来单一文件，代价是引入
一种容器格式、在恢复路径上多一个解析器，并且看不出是哪张表出了问题。一表一文件还意味着
局部恢复就是恢复一张表，而不是一次解包作业。

## 3. 为什么格式不归 k10r

k10r 自写的 dump 等于把同一批行再描述一遍：它得跟着声明同步维护，它会把 k10r 的字段名带进
任何读这份备份的东西里，而且它过不了备份唯一的那道考题——**能被不是写它的那个程序读出来**。
Parquet 免费给出这一条（polars、duckdb、pyarrow 都能开），而「Vocab 导出成标签」这一规则
让文件不依赖存储的编号表就能读懂。

## 4. 事实表是张表，而这里的第一版答错了

第一版对 `GET /export/37` 答 **501**：边不是 `Document` 行——它们活在图的条目形状里
（`EdgeKey` + `EdgeBody` 帧，`GraphEncode`），而 okm 的桥只读 `Document` 集合——所以就论证
说 k10r 自创的边缘 dump 会是真正那份格式旁边的第二种格式。

那个拒绝对「第二种格式」判断正确，对「缺口在哪」判断错了。漏掉事实的备份不是部分备份，而是
一张内容就是边的图里、只有节点的备份。而形状从来不是疑问：边的端点是（表名、主键）对，它的
声明字段本来就是声明。于是导出面长在 okm 的 `Graph` 上（okm ADR-0034 §3、§4），k10r 的事实表
像别的表一样导出：

- 列：`src_table, src_pkey, dst_table, dst_pkey, predicate`，随后是边声明的字段，最后是承载断言
  props 的 `variant` 列；
- 端点键保持**原始字节**——一张边表横跨各节点集合，没有那张表的声明就解不了它的键；
- `name_of` 通过 catalog 解析 ns，不认识的 ns 给 NULL，绝不猜名字。

## 5. reduce 是自己的派生表

`log__reduces`、`code__reduces`：`(table, reduce, group, value)`，一条 reduce 条目一行。reduce
不是行——它住在自己的槽位族里、持有一个累加器——但恢复离不开它：**恢复出来的表如果水位没回来，
会发出已经用过的 id。** 恢复的日志接着 append 覆盖已有的 `seq`，那是静默的损坏，所以水位跟着
依赖它的表一起走。

## 6. 后果

- 检视和手工恢复不需要 k10r：文件里带的是标签，不是编号。
- 结构化日志可以在裁剪丢掉行之前归档——那张表里，导出同时也是唯一的长期记录。
- 恢复日志/代码表之后要**先重放 reduce 表**（把水位推到文件里的最大值），再允许下一次写。
  这是恢复的义务，不是导出的。
- **恢复没有实现。** okm 有 `import_parquet`，接它是一扇单独的门，有自己的裁决：落到哪个 ns
  （请求点名表，而 schema 要对那张表的声明核对，因为导入是**按列序号**读的）、覆盖还是合并、
  以及文件里的 `Vocab` 标签在目标词汇表里不存在时怎么办（okm 的导入选择拒绝而不是猜——那个
  拒绝是设计，不是疏漏）。
- `parquet` feature 在本构建里常开。这扇门是一等表面不是可选附件，所以依赖（arrow + parquet）
  在构建期付一次，而不是变出第二个、构建方式不同的二进制。
