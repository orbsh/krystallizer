# ADR-0013：备份是一个装着 Parquet 与仓库元数据的包裹

日期：2026-10-20
状态：已裁决并落地 2026-10-20（一表一文件）。**2026-10-22 重裁**：备份是**一个** `tar.zst`，
里面每张表是一个目录（Parquet 数据文件 ＋ Iceberg v2 元数据），恢复是一扇门。§2 的按表粒度、
旧 §4 里「一次备份一个归档包」的否决都被推翻；§7 记录为什么元数据用 Iceberg 而不是 Delta Lake。

## 1. 背景

ADR-0007 定的是：批量读仍然是同一 HTTP 边界上的读——没有管理 CLI、没有第二套存储、不
在数据旁边自创一种转储格式。备份正好就是这样一次读（「这张表的全部」），它留下的问题是
**格式**，不是传输。

两种答法。自创一种（k10r 写 JSON 或 CSV dump），或者用 okm 已经有的桥：okm ADR-0007 的
eager Arrow 导出按行**声明**把一个 collection 变成 `RecordBatch`，`parquet_io` 再写成文件。
只有第二种不会漂：列由「生成键编码与载荷帧的那同一份声明」生成，所以改结构是一处改、
改名不可能只改一边。

## 2. 决策：一个包裹、多张表、仓库元数据

**`GET /export`——一个文件，`application/zstd`，文件名 `krystallizer-backup-<UTC>.tar.zst`。**
解开就是这样的目录：

```
krystallizer/
  catalog.parquet                    # (table, ns)，一张表一行
  <table>/data/<table>.parquet       # 这张表的行
  <table>/metadata/v1.metadata.json  # Iceberg v2 表元数据
  <table>/metadata/<uuid>-m0.avro    # manifest（每个数据文件一条）
  <table>/metadata/snap-<id>-0-<u>.avro # manifest list
  <table>/metadata/version-hint.text # 版本号，让**目录**可被直接读
```

**`POST /import`——同一个文件，原路回去。** 一次请求恢复全部表。

- 搬的是一个文件，查的是多个 Parquet——先前的按表导出让运维去取 N 个文件、还得记住顺序，
  那正是这次重裁要拒掉的成本：备份是一件东西。
- 每张表在「每次写也拿的那把锁」下导出，一次一张，落到临时目录；全部成功之后才打包，中途
  失败是 500，绝不拿出半个包裹。所以包裹是一个快照，而且——与 N 个分散文件不同——里面每张
  表都是同一时刻。
- 容器是 `tar.zst` 不是 zip：这个文件是在 shell 里被处理的（`tar -xf`、`tar -tvf`）。压缩与
  容器住在 `mem-core::bundle`（tar + zstd 两个 crate），**不进 okm**：okm 的元数据写出只认
  一个目录和几个数据文件，不知道归档的存在。于是换容器/编码只动一处，改声明只动另一处。
- 元数据里记的每个路径都是相对表目录的（`data/<table>.parquet`、
  `metadata/<uuid>-m0.avro`），表的 `location` 是 `.`。这就是「备份」与「只在原地能用的
  目录」的区别：导出跑在临时目录里，文件是搬走之后（常常在另一台机器上）才被打开的。所以
  按元数据走路径的读取端必须被告知表搬过家——DuckDB 要
  `iceberg_scan('<dir>', allow_moved_paths = true)`——而 `tests/iceberg_readable.rs` 锁的正是
  这件事：一个服务导出的包裹、在别处解开、由一个从没见过 k10r 的工具读（逐表行数，以及实体表
  里的标签）。
- 包裹里的**地址是表名**，不是 ns。ns 是存储自己的寻址（ADR-0010 §1 的 ns 词汇）：它在**库内**
  标识一张表，对打开文件的人没有意义。名字声明在 ns 声明的地方——okm `#[ok_name]` →
  `Document::TABLE_NAME`，与 `#[ok_ns]` 同处——所以两者不会漂，改名不动任何已存字节。
- catalog 是 name↔ns 方向的那张表，落在根上：纯分析用不到它（导出的列已经自带标签），导入要用，
  任何「ns 41 叫什么」的问题也要用。它由同一批声明、同一趟生成，不是第二张要同步维护的表。
- schema 是 okm 的，不是 k10r 的：带类型的列、`Vocab` 字段导出成它的**标签文本**（没有名字的 id
  给 NULL）、定宽声明字段按宽度、`Vector` 字段按不透明的帧字节。k10r 只决定导哪些表、目录怎么
  摆、怎么打包，别的不碰。
- **`GET /export/{table}`** 保留，作检视用：一张表、一个 Parquet 文件、不带元数据。它不是备份的
  形态。读的门可以便宜地多开几扇；写的半扇只留一扇，于是「用文件写满一个库」只有一条路。
- 空表仍导出一个合法的空 Parquet——「这张表是空的」本身是备份该带的信息；检视门上的未知表名是
  404，并指向包裹。
- 行的**开区间**以 `variant` 列随行：声明字段仍是带类型的列，动态段（边的 props、实体的属性）
  是旁边的一列。没有它，文件只带每行的类型化半个、把其余悄悄丢掉——这扇门的第一版就是这样。

**粒度：一个包裹里一表一组文件。** 「一次备份一个宽 Parquet」做不到——一个 Parquet 文件只承载
一个 schema。假装能做的那个变体（把所有表的列并成超集再加一列 `table`）会丢掉让 okm 导出让
人信任的那条性质（文件**就是**声明），并把恢复变成一次重新切分作业。

## 3. 为什么格式不归 k10r

k10r 自写的 dump 等于把同一批行再描述一遍：它得跟着声明同步维护，会把 k10r 的字段名带进任何读
这份备份的东西里，而且过不了备份唯一的那道考题——**能被不是写它的那个程序读出来**。Parquet 免费
给出这一条（polars、duckdb、pyarrow 都能开），而「Vocab 导出成标签」让文件不依赖存储的编号表就
能读懂。

## 4. 事实表是张表，而这里的第一版答错了

第一版对 `GET /export/37` 答 **501**：边不是 `Document` 行——它们活在图的条目形状里（`EdgeKey` +
`EdgeBody` 帧，`GraphEncode`），而 okm 的桥只读 `Document` 集合——所以就论证说 k10r 自创的边
dump 会是真正那份格式旁边的第二种格式。

那个拒绝对「第二种格式」判断正确，对「缺口在哪」判断错了。漏掉事实的备份不是部分备份，而是一张
内容就是边的图里、只有节点的备份。形状从来不是疑问：边的端点是（表名、主键）对，它的声明字段本来
就是声明。于是导出面长在 okm 的 `Graph` 上（okm ADR-0034 §3、§4），**导入的镜像也长在那里**
（`Graph::from_record_batch_table`）：

- 列：`src_table, src_pkey, dst_table, dst_pkey, predicate`，随后是边声明的字段，最后是承载断言
  props 的 `variant` 列；
- 端点键保持**原始字节**——一张边表横跨各节点集合，没有那张表的声明就解不了它的键——所以导入把
  名字解析回 ns，把原始键原样递下去；
- `name_of` 通过 catalog 解析 ns，不认识的 ns 给 NULL，绝不猜名字；导入对不认识的名字是**按行
  拒绝**，绝不凭空造一个集合；
- 边的 id 走键列，所以恢复保留备份里的 id，而不是重新编号。

## 5. reduce 是自己的派生表

`log__reduces`、`code__reduces`：`(table, reduce, group, value)`，一条 reduce 条目一行。reduce
不是行——它住在自己的槽位族里、持有一个累加器——但恢复离不开它：**恢复出来的表如果水位没回来，
会发出已经用过的 id。** 恢复的日志接着 append 覆盖已有的 `seq`，那是静默的损坏，所以水位跟着
依赖它的表一起走；导入取两个累加器里**较大**的那个：恢复绝不下调水位，因为调低就会重发活行还
带着的 id。

## 6. 恢复：按 key 并，签发者跟着行

`POST /import` 走**与活路径同一份写契约**（`put`、`link_into`、`put_fields_into`、reduce 条目），
顺序由 catalog 声明——节点和人在命名它们的边之前，水位在它统计的行之后。运维不用排文件顺序。

- **只并，不清。** 同 key 覆盖，新 key 插入；这扇门永不删。一扇能清空库的门，就是一个打错字能
  毁掉库的门；而并是幂等的——恢复做了一半，再跑一遍就补齐。「从零开始」是部署动作（换一个
  `storage.data-dir`），不是端点。
- **签发者事后从库里重算**（`GraphStore::reseed`、`LogStore::reseed`、`CodeStore::reseed`）：下一个
  节点 id、下一个边 id、社区序列缓存、日志的 `seq`、代码 id。少了这一步，恢复出来的库会发出恢复
  的行已经占着的 id——正是 §5 水位规则防止的那件事，只是高了一层。
- `Vocab` 列带回来、而目标词汇表没有的标签，会在目标里 **intern**（okm 的导入就是这么做的，恢复行
  里的编号是目标自己的编号）。这里先前的文字预测它会拒绝：那既错看了 okm，也错看了恢复想要什么
  ——快照带的是名字，不是编号。
- 失败的导入是**部分**导入：已经写进去的行留着。并的语义正是让它安全的原因（改对、重跑）；不假装
  跨表有事务。
- 拒绝都是调用方的 bug：body 不是 `tar.zst`、归档里没有包裹目录、条目会逃出恢复目录、catalog 点名
  而归档里缺的成员、列集合不是这张表的声明、本库没有那个端点集合。
- 社区序列（`ns 38`）作为一张表在包裹里。它是**签发者**不是数据：没有它，恢复出来的图会重发恢复
  节点已经带着的社区 id。

## 7. 为什么元数据是 Iceberg 的，不是 Delta Lake 的

两者都是「一份 Parquet 文件的日志」。对快照形态的导出，Delta 的日志确实更小：三行 JSON
（`protocol`、`metaData`、`add`）、没有 Avro；Iceberg 要一份元数据 JSON ＋ 一个 manifest ＋ 一个
manifest list，并且要求 Parquet 文件里带列 **field id**。

裁决仍然是 Iceberg，用的判据是这个仓对一切耐久之物花的那条——**这份文件在若干年后仍然必须能被
当成什么读**：

- Iceberg 贵的那一半，是 manifest 的 Avro 编码加 spec 的 field id，这一半已经写好并被读取端验过
  （DuckDB `iceberg_scan`、pyiceberg）。这笔成本已经沉没，Delta「第一刀更便宜」不再换来任何东西。
- Iceberg 的读取端在变宽，它的 REST catalog 正在成为默认，主流仓库原生读它；Delta 的开源势头更薄，
  新特性先在引擎里落地。备份格式是一个长期承诺，这个仓不该在一年后重写这个承诺。
- 增量导出（还没做）正好是 Iceberg 自己的形状：新一次导出是 snapshot N+1 指向新的 manifest list，
  旧快照仍可读。Delta 同样做得到，所以这不是区分点——它只解释了为什么我们把「快照」当作建模单位。
- Delta 真正赢的那点——日志人能 `cat`——不值得换：manifest 也能被文件交给的那些工具读，而没人靠读
  日志去排查五年前的备份。

两者打平的地方：多表访问。谁都不会给你一个不靠 catalog 服务就能指过去的仓库，所以包裹里带
`catalog.parquet`，每张表都是一个自描述的目录（DuckDB 按目录读一张表，pyiceberg 按元数据路径读，
想要 catalog 的消费方把表注册进自己的）。

## 8. 后果

- 检视和手工恢复不需要 k10r：文件里带的是标签，不是编号；元数据是公开的 spec。
- 结构化日志可以在裁剪丢掉行之前归档——那张表里，导出同时也是唯一的长期记录。
- `parquet` 在本构建里常开；归档相关依赖（tar、zstd）只属于 mem-core：okm 不引入压缩、不引入容器代码。
- 这次重裁之前取的按表备份，`POST /import` 读不了。生产前：不存在这样的备份。
