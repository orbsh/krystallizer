# 设计方案：图原生的知识结构（簇、索引节点与入口）

这份文档是一份设计方案，不是设想。它把知识（设计、决策、经验、待办）与代码放进同一个图里导航，前提是：图不是文件的补充索引，而是这些知识**居住的地方**——替代的是"用文件名和目录去定位"这件事，不是字节本身。

两条贯穿全篇的结构决定：**分组分两类**（实体用节点，标注用成员表），**底图不因分组而改变**（算法在干净的图上运行）。

词汇先行，因为没有一套稳定的词，后面的机制会一直漂。

## 词汇

```
簇       声明的关切范围（设计 / 代码 / 待办 / 经验 / 原则 / 问题）。成员是边，节点由端点导出；
           一条边可以同时属于多条簇；成员关系有类型；归属不唯一
索引节点   簇内那个虚拟的多入口节点：无外部实体、成员是图中节点、可嵌套、禁止成环
社区       一种簇：成员由 LPA 发现出来。簇是声明的成员集合，社区是它发现出来的那一类
入口       查询的起点。入口所在的簇决定这一次遍历的排序依据
节点 / 边  普通实体与断言：一条边一个断言，节点是概念
```

  没有几何含义的词是有意选的：簇、索引节点、社区、入口都是软件里已有的说法，不需要读者先建立一幅画面。"局部可导航、全局没有统一坐标系"这件事，用入口与簇就能说清，不必引入流形之类的隐喻。

## 分工：哪些分组属于记忆层，哪些属于存储层

  本文只管记忆层的分组——**簇**与**索引节点**。簇是「这些边属于同一个关切」的声明，成员是边；索引节点是「这些概念构成一个入口」的声明，成员是节点。两者都是声明的、都出现在导航里，区别只在成员是什么。

  另一类分组——社区、事件涉及的事实集合、子图、权限边界——**不是记忆层的概念，是存储层的形状**：它们的成员是边，而不是概念。那一半的布局（成员行、固定面、版本、删除契约、子图代数、多分辨率收缩）由 okm 的 `docs/ideas/hyperedge-membership.md` 承载，本文只定它们的**语义归属**：社区是发现的、簇是声明的，两者不混用（见下节）。

## 一块文档怎样进图

一份决策记录不是一条原子事实，也不该被拆成原子事实。它按**论证单元**切块，块与块之间靠它与其它知识的关系连起来，而不是靠顺序连起来。

```
文档节点    标题、状态（draft / accepted / superseded）、source（路径 @ commit）
块节点      一个论证单元：主张 + 依据 + 后果；带偏移（起点/终点）与内容哈希
归属        块节点进 design 簇或 decision 簇，可同时进两条
拼回        按偏移切原文拼接，断言哈希相等 —— 这是保真的检验，不是可选项
编号        降级为属性（外部引用仍写路径或编号，由节点解析）
```

  块的大小由两条检验定：**能否被单独引用**（"见第 3 段"说得通）、**能否被单独推翻**（这一块的结论被否而邻块仍成立）。两条都过就是一块；只有前者过，通常该并进相邻块。

  顺序不入图。文本的线性是"文本"这个载体的性质，不是知识的性质；真正有方向的顺序只有因果与时间，它们用专门的边（`causes`、`precedes`）表达，不用 `next`。

## 索引节点：整套结构的支点

多入口是这套设计最强的机制，也是最需要规范的地方——没有规范，它会退化成"什么都能连到一切"。

```
1  无外部实体    成员只能是本图中的节点；外部世界的东西必须先被投影成节点
2  成员边有类型  支撑 / 反驳 / 约束 / 案例 / 来源 / 派生，不接受 related_to
3  无位置语义    顺序不入键、不入排序；因果与时间用专门的边
4  可嵌套但禁环  DAG 校验在写入路径上做，不在查询期做
5  归属不唯一    同一节点可以属于多个索引节点，各自带不同的关系类型与权重
```

  第 1 条是范围的闸门：它把"无限扩大"挡在外面，也保证了遍历的每一跳都落在一个已知的节点类型上。

  由此可以举一个真实形状：一条**主张**作为核心节点；一条**经验**作为索引节点指向它（经验本身指向其它节点）；一条**基础原则**作为跨越多个项目的超级索引节点也指向它；若干**内部约束**同样指过来。于是"这条主张的依据是什么"沿入边走，"这个原则有哪些案例"沿出边走，两个方向都是局部的。

## 代码：外部实体，靠投影进图

代码与文档不同，它有独立的存在（编译、运行、被 git 追踪），所以图中放的是**结构投影**，不是代码文本。

```
组件      graph builder，每语言一个后端，输出统一形状
供给      rustdoc JSON / LSP / tree-sitter，按语言能力降级
节点      module / type / fn，带源文件与行号、commit 戳
边        contains（结构）、calls（调用）、governs（这条设计管辖哪些代码）、implements
同步      每次提交重建；过期即重建，不手工编辑
盲区      宏展开、trait 动态分派、条件编译、eval —— 边不全，这些位置回落文本搜索
```

  把语言能力差异关在这个组件里，图本身只认统一形状；否则多语言支持会渗进模型层。

  收益是 token 成本：导航一次只读当前层的摘要（标题 + 一行说明 + 邻居数），而不是把一个文件甚至一个目录的原文读进来。

## 导航

```
入口      项目节点，或一个待办，或一条主张 —— 都是入口
路径      入口 → 所在簇的索引节点 → 成员列表（标题 + 一行摘要 + 邻居数）→ 选定 → 下一层
跨簇      从 design 簇的一个概念，沿 governs 反向走到 code 簇的节点，定位实现位置
锚点      入口 id 可以记住，重复访问不必重新搜索
```

### 入口不是一种类型，是一种角色

需要标记，但不该给节点加一个"入口类型"或布尔字段。理由是它和 ADR-0029 同一条纪律：类型回答"这是什么"，角色回答"它在这里做什么用途"。同一个概念既可能是设计的簇的一个普通节点，也可能是一个好的**起手处**——把它变成 `EntryConcept` 会让类型系统承载用途，而用途是会变的。

所以入口是**索引节点上的成员关系**：

```
簇入口索引   design / code / todo … 每条簇一个入口索引节点（本身也是索引节点）
成员边       entry_of（从入口索引指向候选起点），边上带一句"从这里进来是找什么的"
排序         按该簇的排序规则（design 按反向边数，todo 按阻塞拓扑序）
撤回         删一条边即可，不需要扫描全图找 is_entry 标记
```

  这样"选一个入口"就是打开某个簇的入口索引，读一屏；而不是靠搜索，也不靠在每个节点上维护一个会腐坏的布尔值。同一节点可以同时是两三个簇的入口，各自带不同的进入说明——这正是多父的用处。

  全局锚只有一个需要硬编码：**根节点或项目节点**。LLM 手里必须有一个确定的 id 才能开始，这一个可以进提示词或配置；除此之外不应该有任何写死的 id。

  成本几乎全在**扇出**，不在深度：

```
每层候选 ≤ 7±2；每项约 20–30 token（标题 + 一行摘要）
导航成本 ≈ 层数 × 扇出 × 每项开销
扇出失守时，导航退化成"每层读完所有子节点"，这时它比字符串搜索更差，因为还多走了几跳
```

  所以"事实不能太细"这条旧原则可以退休，取而代之的是**扇出约束 + 标签纪律**：细不细不再决定能不能定位，能不能定位取决于每一层的候选是否可判别。标签纪律包括：节点标题说清"它是什么"、边类型受控（几十个，不允许 related_to）、索引节点的成员列表必须能在一屏内读完。

## 排序：由入口所在的簇决定

  同一个节点，从不同的簇进入，排序依据不同——这不是不一致，这是它该有的样子。

```
design 簇     反向边数（多少主张/原则/约束指向它）= 结构重要度
experience 簇 base + live（累计确立度 + 当期热度）
decision 簇   取代链 + 时间（现行 > 已取代；新 > 旧），不看热度
todo 簇       未完成 + 阻塞关系的拓扑序
```

  四套都是单调关系或拓扑序，没有需要标定的分数。**不要**去做一个跨簇通用的自适应权重：那等于回到"给分数找一个合理值"，而按簇选依据是规则，可解释也可复现。

  唯一带统计的是"结构重要度"（反向边数），它容易被枢纽概念拉满，可能需要按簇内规模归一。这一条要在一份真实语料上跑过再定。

## 与社区的关系

  社区（LPA）发现的是"哪些东西在用中聚在一起"，簇声明的是"这些东西属于哪个关切"。两者都在，但用途不同：

- 簇：确定性的、可预先给出的访问结构，导航走它；
- 社区：随使用漂移的聚合视图，只服务检索（召回时按社区切片组织结果），不做归属判定。

  把社区当簇用，等于让"过去"随"现在"改变；把簇当自治聚类用，等于放弃了确定性。

## 召回：以社区为单位返回，而不是以点为单位

向量召回给的是**点**，而记忆要给的是**上下文**。所以召回之后还有一步：把这些点所属的社区找出来，按命中密度排序，取前几个社区作为结果——一个点可能只是噪声，三十个点同属一个社区则是主题。

社区本身是簇，一次社区发现（LPA 之类）跑完就写成簇：一个社区一个簇，成员是它归到一起的那些边，簇的载荷记下这次运行的元信息——算法、参数、产出时间。于是「不同算法、不同参数的结果」不必互相覆盖：同 `kind`、不同 id，各自带自己的载荷，可以并存、比较，满意了再把旧的那批删掉。

召回时的算法很短，因为它只用两个已有的动词：

```
100 个召回点 → 每个点的关联边 → 边所属的簇（0x0D 面，按句柄有序）→ 计数
30 / 20 / 10，其余散落两三个 → 取前三个 → 展开成员（或只留采样点）→ 格式化成 md
```

节点属于哪个社区是**推导**出来的，不是存下来的：簇的成员是边，节点的社区就是它入边与出边所属的簇。所以不需要为“节点→社区”再造一张面，也不会出现节点归属与边归属不一致这种状态。

簇的成员数可以是零、一或更多，全是合法状态：**簇是一个范围，范围本身就是信息**。“这个问题很敏感，不要问”、“这里曾经有东西，现在没有了”，都是只有簇、没有成员也成立的陈述。所以成员跌到一个时不会自动清除，也没有“减到<n就删簇”这种额外的级联逻辑——要它消失就显式删它。

一次运行与它产出的社区分两层：运行本身是一个簇（载荷记算法、参数、产出时间），社区是它的子簇（`parent_id` 指向运行）。这样某个社区被收缩到没有成员时，运行记录仍然在；多组参数并存就是多个运行簇，按产出时间排序、按参数筛选，淘汰时删整棵子树。

还有一个边界属于应用：**取前几个、是否展开、并列怎么断**都是召回策略而不是存储语义；okm 只提供让它便宜的那两个动词。

## 为什么按簇召回，而不是从种子点遍历

遍历看起来更自然：从一个召回点出发，沿着边跳几圈，把邻域取回来。代价藏在三个必须拍板的参数里，而它们都没有正确答案。

**跳数 k。** 图的密度不均匀：同一个库里有人只连了两条边，有人连了两百条。取 k=2，稠密处的邻域跑成几千行；取 k=3，稀疏处才刚好把上下文凑齐。没有一个全局的 k 是对的，按密度自适应又需要先知道局部度数——那就是一次额外读取，等于把问题推后一步。

**节点预算。** 用“最多取 N 个节点”兜住上面的失控也不行：记忆本身就长短不一，一条短记忆的完整上下文可能是四十个节点，一条长文档的摘要也可能是五个。N 与内容无关，它是给引擎的补丁，不是语义。

**环。** 图里有环，遍历就必须带 visited 集合，否则直接挂。带上之后终止条件变成“visited 与预算、深度、方向共同决定”，行为不再能用一句话解释，也不再能复现。

成本形状的差异更硬：

| | 从种子点遍历 | 按簇召回 |
|---|---|---|
| I/O | k 轮随机点读，行数按度数爆炸（度数 20、k=3 约八千行） | 每簇一次顺序前缀扫，总量由社区大小决定，与度数无关 |
| 端点的来路 | 每跳一次前缀扫，键里就是句柄；只有真要按属性过滤或格式化时才回表 | 每簇一次前缀扫，键里就是两端；同样只在需要内容时才回表 |
| 结果的性质 | 路径集合：随起点、方向、k 变化 | 成员集合：只由社区发现决定 |
| 可复现性 | 取决于 visited、预算、遍历顺序 | 给定簇即确定 |
| 每跳的决策成本 | LLM 导航要每跳推理一次 | 零次 |
| 需要的训练 | 导航模型与标注数据 | 无 |
| 离线成本 | 无 | 一次社区发现，O(边数) |

两条路都不回表：图内部的跳转全程在句柄上，回表只发生在需要节点内容的时候（按属性过滤、格式化输出），而且那时也不是“每跳一次”，而是对最终要用的那批节点做一次批量解析。差别不在回不回表，而在**扫描的形状**——遍历是每层一点、点数按度数扩散，按簇是一次一条连续区间。

一句话：**遍历把“邻域”表达成路径，按簇把“邻域”表达成集合。** 路径受跳数与方向支配，集合不受；路径的代价随密度变化，集合的代价随社区大小变化。

诚实的局限有两条。第一，簇需要离线先跑一次社区发现，召回时读的是那次运行的结果——它不会自动追上最后一秒的写入。第二，**跨社区的关系看不见**：两个社区之间的桥接（一个人把两个圈子连起来）在按簇召回里表达不出来，遍历能看见。

两条局限都指向同一种处理：**混合，但按内容类型分，不按查询分**。

**落到簇外的新节点，对它做有限跳。** 刚写入、还没被任何一次社区发现覆盖的节点不在任何簇里，按簇召回会漏掉它们。对这些点单独走几跳是安全的，因为它们恰恰排除了稠密区——正是稠密让跳数不可定，而新点与孤立点的度数低，跳数可以取一个小常数，走到已有社区或走完为止。反过来说，只有在“已确定落在一张稀疏的子图里”时跳数才是可定的参数，这正是这里成立、全局遍历不成立的原因。

**结构化内容本来就用遍历，簇对它没有意义。** 任务图、结构化的 skill、依赖链，这类内容的语义就是路径：任务 A 之后是 B、skill 第 3 步依赖第 2 步的输出。把一条 skill 的步骤压成一个“社区”，会丢掉顺序，而顺序就是它要表达的全部。所以召回策略按内容类型分派——非结构化的记忆用簇（集合），结构化的工件用遍历（路径）——一次召回里两类结果各自成型，再合并。

这条分派不是妥协，它承认两件事：集合适合回答“关于什么”，路径适合回答“然后呢”。

## 开放问题

1. **块边界由谁定。** 一次性 LLM 分块 + 上述两条检验作为规则；之后的编辑如何增量重建（按内容哈希判断哪块变了）。
2. **文档编辑的保真回路。** 拼回断言哈希相等 —— 谁在什么时候跑这个断言（写入时？读取时？重建时）。
3. **多语言代码投影的优先级。** 先做一种语言跑通再铺开，还是先做统一形状的多后端骨架。
4. **索引节点环检测的成本。** 写入路径上做 DAG 校验需要一次反向遍历，与写入延迟的权衡。
5. **簇的版本化。** 簇的种类词表增加一条簇时，历史节点的归属是否需要迁移。
